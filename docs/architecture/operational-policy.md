# Rete 運用ポリシー

Rete の運用観点の前提を集約する。機能追加時に「ログはどう出すか」「失敗時どう振る舞うか」「env var をどう足すか」を毎回判断せず、本ファイルの方針に従う。譲渡先の開発者も本ファイルを参照する想定。

構造的不変条件は [`architecture-invariants.md`](./architecture-invariants.md) に集約する。本ファイルはその運用層の兄弟ポリシーである。ReteはReferenceのサテライトであり、接続境界の方針を揃える。

**発火条件**: 以下に着手する時、本ファイルを参照してから実装する。

- 新規外部依存（npm package / SDK / 外部 API / Queue / Cron）
- 新規 env var 追加 / 必須化 / placeholder 値変更
- 新規 error code / error 応答 shape 変更
- 新規 log 出力 / log level 変更
- healthcheck endpoint 関連
- 認証境界・role 変更
- データ保持・削除ロジック変更
- 非同期処理追加（fire-and-forget 判断が必要）
- 通知連携追加（Slack / メール / Sentry 等）

---

## §1 エラーハンドリング一元化

構造的不変条件の「Errors and security」に従い、モジュール内へ汎用try/catchを散らさず、上位filterで共通処理する。

- **全例外**: `AllExceptionsFilter`（`packages/backend/src/common/filters`）
- **Prisma 固有**: `PrismaExceptionFilter` — P2002 (conflict) / P2003 (foreign key) / P2025 (not_found) / P2034 (write conflict) / P2028・P2024 (tx timeout・接続待ち超過)

応答 shape（HTTP エラー時）:

```json
{ "success": false, "error": { "code": "UNAUTHORIZED", "message": "...", "details": {} } }
```

error code 体系: `VALIDATION_ERROR`(400) / `BAD_REQUEST`(400) / `UNAUTHORIZED`(401) / `FORBIDDEN`(403) / `NOT_FOUND`(404) / `CONFLICT`(409) / `WRITE_CONFLICT`(409) / `TOO_MANY_REQUESTS`(429) / `INTERNAL_ERROR`(500) / `SERVICE_UNAVAILABLE`(503)

- 認証導入により `UNAUTHORIZED` / `FORBIDDEN` を実使用する。OIDC interaction（login/consent）の失敗も本体系に乗せる
- 新規 error code を足す場合は本表に追記し、対応 filter を更新する
- **status からの code 導出は「例外が `code` を明示していない時だけ」効く**（cmn-0235）。明示 `code` を持つ例外（MFA 専用 code / `PASSWORD_CHANGE_REQUIRED`(403) / `IP_NOT_ALLOWED`(403) / 下記 `WRITE_CONFLICT` / `SERVICE_UNAVAILABLE`）はそのまま応答へ載る。同一 status に複数の意味がある経路を画面が出し分けるための規約
- **`WRITE_CONFLICT`(409)**（cmn-0235）: Serializable(SSI) の write conflict（Prisma P2034）がクライアントまで抜けてきた場合（`runInSerializableTransaction` のリトライ上限でも解けなかった場合。直列化 tx は全経路が同ヘルパ経由に統一済み＝cmn-0251。ヘルパを経由しない直列化 tx を新設するとリトライなしで即到達するため、新設しないこと）。操作自体は正しく再送で通る性質のため 409。一意制約違反由来の `CONFLICT`(409) と `code` で区別する
- **`SERVICE_UNAVAILABLE`(503)**（cmn-0235）: interactive transaction の timeout 超過（P2028）/ 接続プール待ちの超過（P2024）。一時的な混雑であり再送で解けるため 503 + `Retry-After` ヘッダ（既定 5 秒）を返す。503 は 5xx として既存の error ログ経路にも乗る（リトライの warn ログとは目的が違うため二重計上を許容）
- **`TOO_MANY_REQUESTS`(429)**（hardening H6 / ADR 0033）: ①`@nestjs/throttler` のレート超過（throttler 由来は `code` を持たないため `AllExceptionsFilter` が status から導出）②ログイン試行ロックアウト（passwordまたはMFAの連続失敗で Account をロック中・`code: TOO_MANY_REQUESTS` を明示）。ロックアウトは email 実在を 429/401 の差で確認できる論理リークを伴うが、UX 説明性を優先して許容（ADR 0033）
- **例外（status-check endpoint）**: `GET /auth/me` は未ログインを 401 にせず `200 + data:null` を返す。未ログインは正常状態であり、401 はブラウザの抑止不能な console error（Next dev tools「N Issues」累積）を生むため。**保護リソースの 401 は不変**。詳細は ADR 0030（rete-files-0024）
- **MFA 専用 error code（ST-2-2 / ADR 0040）**: 上記汎用体系に加え、2 段階ログイン・MFA 設定経路で意味を持つ専用 `code` を `HttpException` body へ明示する（`AllExceptionsFilter` がそのまま統一 shape に載せる）:
  - `MFA_REQUIRED`(401) — パスワード検証は通ったが TOTP 未入力（`/auth/login` が `{mfaRequired:true}` を返した後、`/auth/login/mfa` を pending 不在で叩いた等）。フロントは 6 桁コード入力へ誘導
  - `MFA_INVALID_CODE`(401) — TOTP / バックアップコード不一致（confirm / disable / regenerate / login/mfa 共通）。login/mfaの失敗は throttle(5/60s) + Account単位lockout（既定5回/15分）+ pending上限5で抑制。confirm/disable/regenerateはthrottleで抑制
  - `MFA_SETUP_REQUIRED`(403) — 全体強制 ON かつ当該 account が MFA 未設定（`MfaEnforcementGuard` が保護ルートを遮断）。`/auth/login` も session 確立後に `{mfaSetupRequired:true}` を返し設定画面へ誘導

## §2 ログ方針

- **NestJS 標準 `Logger`**（context prefix: `new Logger(ClassName.name)`）、出力先 stdout。pino/winston は不採用
- `console.log` は使わない（context prefix が失われる）
- **センシティブ情報を log に出さない（認証実装で特に厳守）**: password / passwordHash / `SESSION_SECRET` / `OIDC_COOKIE_KEYS` / jwks 秘密鍵 / access・refresh・id token / authorization code
- log level: `error`（未処理例外・外部依存失敗）/ `warn`（リトライ可能失敗・設定不整合・**ログイン失敗**）/ `log`（起動停止・**ログイン成功**・主要ライフサイクル）/ `debug`（開発時のみ）
- **404 応答は warn で 1 行残す（fil-0157）**: 存在しない対象への総当たり走査（IDOR 探索）の痕跡が無いと攻撃の試行自体を検知できないため、`AllExceptionsFilter` が 404 だけを `warn`（`<method> <path> -> 404 <code>`）で記録する。残すのは操作種別・URL の path 部分・エラーコードに限り、**query 文字列（検索語・器の id 等）・request body・利用者識別子は出さない**。500 未満のその他の状態（401/403/400 等）は従来どおりログしない（ノイズ回避）

## §3 依存障害時の挙動

### 止める側（必須経路、失敗時は業務エラー）

- **DB (PostgreSQL)** — Prisma 経由
- **認証 / 認可** — passport guard・express-session・OIDC Provider
- **OIDC の永続化** — grant / session / authorization code を保存する DB アクセス
- **ファイルストレージ（ローカル FS 実体）** — ファイル実体の read/write（`FILE_STORAGE_ROOT` 配下）。アップロード保存・ダウンロード読み出しは必須経路で、失敗時は業務エラー（容量・I/O エラーは `INTERNAL_ERROR`）。実体アクセスは `StorageService` 抽象越しに行い、後で S3 等へ差し替えられる境界を保つ（Phase FB で導入）
- **アップロード必須経路の**「**止める側判定**」**として追加**: **内容署名検査（fil-0140）**。`magic-bytes.js` で拡張子偽装と実行形式（PE/EXE・ELF・Mach-O）の混入を保存前に拒否する。ファイル先頭バイトのみを読み（diskStorage の RAM 全量保持なし・fil-0121 維持）、依存障害時はアップロードを業務エラーで止める。判定不能な形式はクライアント申告 mime を維持して通過させる（後方互換）。適用箇所は `POST /files/folders/:id/files` と `POST /files/files/:id/versions` の両 upload 経路（fil-0140）。

### 止めない側（fire-and-forget、失敗時は `logger.error` で痕跡のみ）

- **OIDC payload の定期 purge**（`OidcPurgeService`・`@nestjs/schedule` の日次 cron）— 期限切れ行の物理削除。バックグラウンドジョブは HTTP 例外 filter の対象外のため service 内で try/catch し、失敗してもアプリを止めず `logger.error` で痕跡を残す（catch を握り潰さず必ずログ）

新規外部依存を追加する時は、依存障害時に対象機能またはアプリ全体を「止める / 止めない」のどちらにするかを実装前に宣言する。

### reference 起動確認 probe（止めない側・クライアント実施）— rete-files-0037 / common-0018

共通シェル「システム」タブ（reference frontend への外部遷移）は、env の available（`REFERENCE_OIDC_READY`）が立っていても reference dev サーバーが未起動なら遷移が `ERR_CONNECTION_REFUSED` で空振りする。これを防ぐため、**rete frontend がクライアント側で reference オリジンへ no-cors fetch の reachability probe を投げ**、到達不能ならタブ／system お気に入りを非活性（灰色）にする（`useReferenceReachable`）。

- **「止めない側」**: probe は best-effort で、失敗しても rete 本体機能は一切止めない（空クリック防止の UX ガードのみ）。確認前は楽観的に有効（グレー点滅回避）。
- **backend の menu 描画（getMenu）には probe を載せない**: 毎回の menu 取得に cross-origin 往復・遅延・タイムアウト処理の結合（コスト）を負わせない判断（common-0018 案A を不採用）。確認はクライアントで完結し、reference 側に CORS 設定を要求しない（no-cors）。
- **probe 先オリジンは CSP `connect-src` に必須**（`NEXT_PUBLIC_REFERENCE_APP_URL`）。未追加だと CSP がブロックし、reference 稼働中でも永続グレーになる。

### secret の扱い（認証で重要）

- `SESSION_SECRET` / `OIDC_COOKIE_KEYS` / `OIDC_JWKS` / `MFA_TOTP_ENC_KEY` は **secret**。`.env.example` には placeholder のみ記載し、実値はコミットしない
- 本番（`NODE_ENV=production`）では factory 側（`oidc-config.factory.ts`）が OIDC_COOKIE_KEYS / OIDC_JWKS の存在を検査して即 throw し、main.ts の validateProductionSecrets が長さ＋placeholder を検査する（二重ガード＝factory は存在・bootstrap は強度）
- env var 名は SCREAMING_SNAKE_CASE
- RP（struct-pass-reference）の静的 client は `OIDC_REFERENCE_CLIENT_SECRET` と `OIDC_REFERENCE_REDIRECT_URIS` が**両方**設定された時だけ登録される（AND 条件・cmn-0230）。どちらか欠ければ client 0 件（既定 secret も既定 redirect_uri も本番に流出しない）。加えて本番（`NODE_ENV=production`）で secret のみ設定し redirect_uris の有効値がゼロの場合は起動時にエラーで停止する（連携を使わない本番＝secret 未設定は従来どおり起動できる）。RP 連携を有効化する時はランダム secret と実 callback URI を揃えて設定する
- seed の既定 admin/demo パスワードはソースに平文で存在する公開値のため、production では `SEED_ADMIN_PASSWORD` 未設定で seed を停止する（`seed.ts` の fail-fast）。譲渡先・本番は必ず強い値を設定する
- compose の runtime environment 渡し（`.env.production` → `environment:`）は `docker inspect` で平文可視。単一運用者ホストでは許容し、将来の hardening 候補として compose secrets 化を検討する（cmn-0416）

### session ストア（**対応済み 2026-06-03** — DBT-8 / ADR 0010 resolved）

- **dev**: express-session は既定の **MemoryStore**（`SESSION_STORE=pg` で pg に切替可）。プロセス再起動で全ログアウト・複数インスタンスで session 不整合・メモリリークがあるため**本番不可**
- **本番**: `connect-pg-simple` で既存 PostgreSQL（`session` テーブル）に永続化。`createSessionStore`（`src/common/session/session-store.config.ts`）が `NODE_ENV=production` で常に pg ストアを返し、`main.ts` は永続ストアを解決できなければ **fail-fast で起動拒否**（旧 `logger.warn` 経路を解消）
- **session テーブル**: Prisma migration（`model Session` → `session`、列は connect-pg-simple 固定スキーマ `sid`/`sess`/`expire` に一致）が作成する。ライブラリ自動作成（`createTableIfMissing`）は使わず `false` 固定 → migration 履歴が単一ソース
- **OIDC provider 側の session/grant** は別系統で、OIDC adapter（`oidc_payloads` テーブル）に永続化済み。express-session（Hub 等アプリ認証用）とは独立

## §5 healthcheck

- **現状（H9・2026-06-13）**: `GET /api/v1/health` は DB readiness 同居（`{ status, db, timestamp }`）。`status`=`ok`/`error`・`db`=`up`/`down`。DB 到達可能で 200、不通で **503**（LB/オーケストレータが unready を検知できる readiness シグナル）。認証不要・`@SkipThrottle()`（probe cadence を rate limit に縛られない）
- **実装方式**: `@nestjs/terminus` は導入せず**自前**（`PrismaService.isHealthy()` が `SELECT 1` を 2s timeout 付きで ping → bool）。reference 側 §5 も terminus 未導入のため「parity 先」が実在せず、`SELECT 1` 1 本に依存を足すのは過剰と判断（ADR 0034）。将来 readiness の対象が増えた（外部依存・キャッシュ等）時点で terminus 化を再検討
- **error tracking**: 外部サービス（Sentry 等）は導入せず**自前**。`AllExceptionsFilter` がサーバエラー(5xx)を request コンテキスト（method/path/status/code）+ stack 付きで `error` level に集約し stdout ログから追跡可能にする。4xx は想定内のため非記録（ノイズ回避）。request.url は CR/LF 除去で log injection（CWE-117）を防ぐ

## §6 データ保持期限・個人情報境界

- **OIDC payload（`oidc_payloads` テーブル）**: adapter は token / session / authorization code を ttl 付きで保存する（ttl は `oidc-config.factory.ts` で明示）。`find` 系は `expiresAt` 超過を読み出し時に弾く（漏洩はしない）が、行自体は自動削除されない。**対応済み（2026-06-03）**: `OidcPurgeService`（`@nestjs/schedule` の日次 cron）が `expiresAt < now()` の行を物理削除する。**保持方針は即時 purge（猶予なし）**＝失効後は保持しない。**無期限行（`expiresAt = null`、`expiresIn=0` で保存される稀なケース）は対象外**として `not: null` で保護する。削除件数は `log` level で出力（センシティブ情報なし）。失敗時は §3「止めない側」に従いアプリを止めず `logger.error`
- **ファイル実体・版（Phase FB）**: 同名再アップロードは旧版を物理削除せず version として retain する（spec §3 案S）。**保持方針＝版は無期限 retain（自動削除しない）**。ファイル削除時の旧版連動・soft/hard delete・保持上限・容量クォータは MVP では未定義（要件が出た時点で書く）。実体は `FILE_STORAGE_ROOT` 配下、メタ／版情報は DB に保存
- **express-session（`session` テーブル）**: connect-pg-simple が内蔵 prune（既定 15 分間隔・`expire < now()` を物理削除）で期限切れ session 行を自動掃除する。**保持方針＝失効後は保持しない**（OIDC payload purge と同思想）。cookie `maxAge` は 1 日（`main.ts`）。session 値（`sess`）には `passport.user`（account IDとpassword hash由来の署名付きcredential version）が平文 JSON で入る。password hash自体は保存しない。パスワード変更でversionが変わるため、旧versionのRete sessionはdeserialize時に無効化される。既存のIDだけのsessionはこの変更の初回deploy時に一度だけ無効化する。MVP では暗号化しない。prune は §3「止めない側」相当でアプリを止めない（ライブラリ内ハンドラ、エラーは `errorLog` 経由で NestJS Logger に出力）
- **退職 / 部署移動 / account 終了時のデータ処理（cmn-0048・2026-06-23 確定）**: MVP/1:1 運用を前提に「重い実装を足さず、ポリシーを明文化する」方針で 4 論点を確定した。
  - **① 退職後の reference セッション失効（OIDC 窓）**: 退職ロック（`isActive=false`）で rete は即ログイン不可になるが、reference（WMS）は初回認証後は自前セッションで回るため最大 24 時間ログインが生き残る「窓」がある。**この窓を自動失効（SLO / back-channel logout）で塞ぐ実装は持たない**（ADR 0008 の見送り判断を退職ケースにも適用＝実装が重く・退職は稀・1:1 運用で実害が小さい）。代わりに**運用手順で補う＝退職ロック後、管理者が reference 側のアカウントも手動で無効化する**。right to erasure 等で即時失効が要件化したら ADR で本設計する。
  - **② 退職者のデータ（タスク担当 / 発話 / ファイル）**: **retain（残す）**。組織の資産として保持し、本人の操作だけをロックする。匿名化・自動移管・自動削除はしない。退職者が担当のままのタスクは**既存の担当割当 UI で管理者が別の人へ付け替える**（新しい仕組みは作らない）。発話は監査・経緯保持のため消さない。
  - **③ 部署移動で不可視化された本人の過去発話（孤児発話）**: **管理者が代理で編集 / 削除して救済する**（本人専用の特別経路は作らない）。**既存実装で機能することを確認済（cmn-0048 製造時・2026-06-23）**＝`assertOwnerOrAdmin`（ADMIN は所有者チェックを常にバイパス）＋ `assertVisibleOr404`（管理者が当該 Space を可視である前提）で、`chat.service.ts` の `updateMessage` / `deleteTheme` / `updateTheme` が ADMIN による他者発話の編集 / 削除を許可する。新規実装は不要。
  - **④ account の完全削除（個人データ消去）**: **条件付きルール＝紐づくデータ（タスク / 発話 / ファイル等）が「ある」account は物理削除しない（soft lock=`isActive=false` のみ）／「ない」クリーンな account のみ物理削除を許可する**。実際の削除 UI / API は MVP では未実装。個人データ削除要件（right to erasure 等）が顕在化した時点で、本ルールに沿って hard delete ＋ OIDC grant 連動失効を ADR で本設計する。
- **監査ログ（`audit_logs` テーブル）**: hardening H5 で横断 interceptor が認可下の mutating 操作（create/update/delete）と login/logout を記録する。**記録方針**: ①**read(GET) は記録しない**（件数膨大化を避ける MVP 判断・将来コンプライアンス要件が出たら再検討）②記録は **best-effort**＝書き込み失敗でユーザー操作を巻き込まない（§3「止めない側」に従い catch + `logger.error` で痕跡のみ）③actor / system は記録時点の値を**スナップショット保存**（ST-6 の非正規化方針・後の改名/削除で過去ログが変質しない＝改竄でないことの担保）④**拒否された操作（4xx）は記録しない**（監査は認可下で成立した操作の記録とし、拒否は状態を変えない。試行を同じ一覧へ混ぜると「起きた操作」の記録でなくなるため、残すなら別の記録類型と保持方針が要る。§5 のとおり 4xx はサーバログにも残さない＝404 を除く。将来コンプライアンス要件が出たら再検討）。**保持方針＝12ヶ月**: `createdAt` が 12ヶ月超過の行を `AuditLogsPurgeService`（`@nestjs/schedule` 日次 cron・`OidcPurgeService` と同型）が物理削除する。失敗時は §3「止めない側」。削除件数は `log` level（センシティブ情報なし）。**12ヶ月の根拠**: 中小テナント運用での一般的な操作ログ参照スパン（四半期×4＋α）を踏まえた既定値で、譲渡先が要件に応じて調整できる単一定数として持つ

## §7 通知・メール送信ルート

運用通知（インシデント検知）と業務トランザクショナルメール（MFA/招待）は性質が異なるため分離して扱う（ADR 0035）。

### 7.1 インシデント / 運用通知

障害・運用通知の**自動配信基盤は持たない**が、周知手段ゼロではなく**段階方針**を持つ（brd-0102 / 案A）。

- **最小（現状で使えるもの）**: 既存**お知らせ機能（announcement・ADMIN 作成／全認証ユーザー閲覧）を運用周知の一次手段として流用**する＋緊急時は手動連絡。お知らせは認証済みユーザーへアプリ内で届くため、計画停止・障害復旧・運用変更の周知に足りる（専用 incident 配信基盤の新設は不要）。即時の新規実装は無し＝既存機能の運用上の位置づけを定めるのみ
- **将来**: Rete 自身が Comm / Chat アドオンを持てば、自プロダクトの障害／運用通知を Rete Chat（または Space）へ流す連携が候補。構造が見えた段階で段階的に拡張する
- **持たないもの（自動配信基盤）**: 障害を自動検知して外部（メール／Slack／push）へ配信する仕組みは持たない。通知方式は譲渡先の運用形態に強依存し、リファレンス側にベース実装を持つと押し付けになる。Company は個人運用で「気付かなくてよい」が許容される。外部 error tracking を持たない判断（§5 / ADR 0034）と同型
- **社外ゲストへの周知到達**: 社外メンバーへの障害周知は §8「board / Backlog の社外境界」の遮断方針と一体（社外には Backlog を見せないため、社外向け周知は将来 Space 導入時に社外用 Space のお知らせ経路で行う）

### 7.2 トランザクショナルメール（招待）— ADR 0035

ST-5（招待リンク）が必要とする外向きメールの送信方針。**MFA は当初モックでメール OTP を想定していたが、認証アプリ（TOTP）方式へ逸脱した（ADR 0040）ためメール非依存**。当面の唯一のメール consumer は招待。

- **送信手段 = env 設定の SMTP 自前送信**。薄い `MailService` 抽象（`nodemailer` 相当）の transport を env から構成する。**外部メール SaaS（SendGrid / SES / Resend 等）は採用しない**（§5 error tracking と同じく譲渡先 lock-in を避ける。譲渡先は任意の SMTP を env で挿すだけで動く）
- **未設定時は graceful degradation**: SMTP 未設定の環境では MailService が「未設定」状態を返し、依存機能（招待）は**起動を止めず無効化**する（fail-fast にしない）。UI は「メール未設定のため利用不可」を明示。メール非依存の最小構成（単一管理者・手動発行）の譲渡先がそのまま動く
- **送信失敗時の挙動（§3 準拠・操作スコープ依存）**: メール送信は**当該操作の必須経路（止める側）**＝送信失敗で招待発行は業務エラーを返す。ただし**アプリ全体は止めない**（他機能無影響）。失敗は `logger.error` で痕跡。**招待リンク token は §2 に従い log に出さない**
- **設定 surface（CM-3-2 で §4 表へ追加済・2026-06-14）**: `SMTP_HOST` / `SMTP_PORT` / `SMTP_SECURE` / `SMTP_USER` / `SMTP_PASS` / `MAIL_FROM`。いずれも任意（未設定＝メール機能無効）。secret（`SMTP_PASS`）は §4「secret の扱い」に従い placeholder のみコミット。dev は docker-compose の **Mailpit**（SMTP 1025 / Web UI 8025）で実メールを捕捉・目視確認する
- **実装（CM-3-2・2026-06-14）**: `MailService`（`src/common/mail`）が `isConfigured()`（host+from 判定）/ `send()`（未設定=`MailNotConfiguredError` / 送信失敗=`MailDeliveryError`）を提供。MFA は TOTP 採用（認証アプリ）でメール非依存のため、当面のメール consumer は招待（ST-5）のみ

## §8 認可モデル（feature ロール境界とリソーススコープ）

機能 API の既定の認可は **認証（`AuthenticatedGuard`）** を土台に、システム管理操作は `@Roles(Role.ADMIN)` + `RolesGuard`、リソース操作は所有者・membership・`UserGroupScopeGrant`・`ScopeVisibilityService` の境界で gate する。旧 `FeaturePermissionGuard` / `@RequireFeature` と feature ロール層は set-0180 で撤去済みであり、現行の認可経路ではない。**リソース単位（object-level）の所有者 / スコープ ACL は機能ごとの実装境界に従う**。

- **files = Desk 統一 Space モデル（チャネル可視＝配下ファイル可視）**: フォルダツリーは Desk の Space と一体で、`Folder.spaceId`（NOT NULL・親子は複合 FK で同一 space を不変条件にする）が帰属器になる。判定は `ScopeVisibilityService.resolveVisibleSpaceIds` が返す可視 Space の集合だけで行い、**可視 Space のフォルダ / ファイルは read / create（版追加含む）/ move / delete のすべてを行える**（VIEW / EDIT / MANAGE の段階権限は持たない＝見えるなら使える）。per-folder の権限機構は持たない（ADR 0063）。
  - 非可視 Space のフォルダ / ファイルは一覧・検索・ツリーから除外し、直接アクセスは **404**（存在秘匿・ADR 0038 準拠。不在の時と文言を揃える）。単一対象も一括経路も同じ境界（`assertFolderAccessible`）を通る。
  - 唯一の ADMIN 限定操作は**ファイル設定の更新**（`maxSizeBytes` / `allowedExtensions` は全ユーザー共通の singleton で、非管理者の改変が全員のアップロードを止めうるため `@Roles(Role.ADMIN)`）。
  - version 番号衝突は P2002→409 の補償削除で正常系ハンドル、fileId 列挙は throttle（20/min）で抑制。
- **chat / tasks / files は同一の可視性レイヤ**: CM-2 `ScopeVisibilityService`（Membership × scope）が唯一の判定主体で、機能ごとに別の認可ユニバースを作らない（architecture-invariants §4）。
- **attachments**: target 個別リソース（タスク / テーマ / タスクコメント / チャットメッセージ）の可視性は `ScopeVisibilityService` で gate し、非可視 Space の対象は一覧（`GET /attachments?targetType=&targetId=`）・作成・解除のいずれも **404**（対象不在と同じ文言＝存在秘匿・ADR 0038）。一覧も対象不在を 404 にし、status から対象の実在を読み分けさせない（容器指定型の一覧は不在も 404・ADR 0082）。DELETE は加えて `assertOwnerOrAdmin` で所有者 guard 済。
- **accounts（`GET /accounts`）**: 認証のみで素通し（id / name のみ返却・email / role / passwordHash は遮断・ADR 0022）。担当者割当 UI 用の業務データのため ADMIN 限定にはしない。
- **board / Backlog の社外境界（brd-0102）**: Backlog タブは別プロセスの instruction-board v2（:3072・`/v2.html`）を iframe 表示する。rete の membership / feature ロール境界は別プロセスの board に及ばない（board 側に rete のアクセス制御は無い）。**方針＝社外ゲストに board(iframe) を見せない遮断**。現状 rete に社外ゲスト / external ロールは未実装（`Account.role`=ADMIN/MEMBER のみ）で board への到達経路自体が無いため、いま追加実装は不要＝方針記述のみ。将来 Space を導入し社外メンバーを受け入れる時は、Backlog（内部運用チケット＝kind:internal 相当）を**社外メンバーに非表示**にする（社外連携は専用ロールを作らず「社外用 Space＋通常権限」で内包する external_collab 方針と整合）。board 自体の認証境界を rete と統合するか／社外 Space からは Backlog タブを描画しないかは Space 導入時に確定する。
- **board の state 遷移記録の actor は自己申告（brd-0225 / brd-0245 MEDIUM 2）**: board の `state_events`（brd-0222）が持つ `actor` は `x-board-agent` ヘッダ（brd-0242）があればその小文字識別子（DS→ds・M2→m2 等）、無ければ `x-board-session` ヘッダの有無で c2 / boss、いずれも無ければ既定 'system'、という優先順で決まり、値の真正性は検証していない（形式検証のみ）＝**識別ではなく主張**。board にはそもそも認証境界が無く（上記の通り rete の membership は及ばない）、既存のセッションロックも同じ前提で動いている。したがって遷移記録は集計・説明の材料として読むに留め、**ゲート判定や権限判断の根拠には使わない**。認証を導入するなら board 全体の認証境界の議論として扱う（ここだけ強化しても境界は閉じない）。

## §9 IP 許可リスト遮断（set-0025 P1 / set-0034 hardening）

ログイン設定（ST-2-3）の IP 許可リストは**保存だけでなく実際に遮断する**（`IpAllowlistGuard`・認証境界の最前段＝`ThrottlerGuard` より前で評価）。挙動:

- **空リスト = 制限なし（全許可）**。1 件以上設定された時のみ enforce し、リスト外 IP は **403 `IP_NOT_ALLOWED`**（自己ロックアウト防止のため "空＝全許可" を guard 側で明示扱い）。
- **fail-secure**: IP 取得不能・CIDR パース不能・family 不一致はすべて拒否側に倒す。DB 例外は素通しせず `AllExceptionsFilter`（500）に委ねる（fail-open で制限を無効化しない）。
- **除外 path**: `/health`（死活確認）＋ **OIDC バックチャネル `/oidc/{token,me,jwks,.well-known}`**（set-0034・下記「OIDC エンドポイントの除外方針」）。厳密 base 照合（`/healthz` / `/oidc/metoo` 等はバイパスしない＝`base` 完全一致 or `base/...` のみ）。
- **クライアント IP の判定元**: `req.ip`（trust proxy 設定に従う）→ socket.remoteAddress。IPv4-mapped IPv6（`::ffff:a.b.c.d`）は素の IPv4 へ正規化してから CIDR 照合する（dual-stack 接続でも IPv4 CIDR が成立する・`normalizeIp`）。
- **許可リスト取得は TTL キャッシュ（15s）**（set-0034）。`IpAllowlistGuard` は APP_GUARD シングルトンなのでインスタンスキャッシュがリクエスト間で持続し、毎リクエスト DB 取得を避ける。**許可リスト変更の反映は最大 15s 遅延**する（自己ロックアウト解除・新規 IP 追加・IP 削除いずれも同様）— 即時反映でなく ≤15s の遅延を許容範囲とする（hardening のトレードオフ）。DB 例外時はキャッシュせず伝播（fail-open しない）。
- **遮断ログ**（set-0034）: リスト外 IP を遮断した時 `Logger.warn` で `IP_NOT_ALLOWED: <method> <path> from <ip>` を残す（§2 ログ方針・warn レベル）。秘匿情報は出さず IP・endpoint のみ。

### デプロイ要件（リバースプロキシ背後で運用する場合・重要）

`main.ts` の trust proxy は**既定 false**（＝`req.ip` はソケット直結 IP）で、`TRUST_PROXY=true` の時だけ hop 1 で有効化される（`main.ts`）。既定は rete の素のデプロイ（1 台直結・X-Forwarded-For を信頼しない secure default＝XFF 詐称によるバイパス不可）に合致する。**nginx/caddy 等のリバースプロキシ背後に置く場合は、`req.ip` がプロキシ IP（127.0.0.1 等）になり IP 許可リストが正しく機能しない**（プロキシ IP がリストにあれば全通過・無ければ全遮断）。その構成へ移す時は `app.set('trust proxy', <信頼ホップ数 or 'loopback'>)` を**正しく**設定すること（過大に信頼すると XFF 詐称でリストをバイパスされる）。

- **残余リスク（trust proxy 有効時の直結詐称・cmn-0416）**: `TRUST_PROXY=true` で運用中に backend へプロキシを経ず直結できる経路が残っていると、接続元が X-Forwarded-For を任意に付けられるため `IpAllowlistGuard` の判定 IP 等を任意化できる。この詐称はコードでは構造的に排除できず、**backend を edge network 経由（Caddy）以外から到達不能に保つデプロイ構成**（deploy-setup.md §1）が前提条件になる。

### OIDC エンドポイントの除外方針（set-0034）

rete を OIDC IdP として使う SSO（struct-pass-reference RP）で、`nest-oidc-provider` は `@Controller() @All('/*')` の catch-all で Nest ルート化されるため **`/api/v1/oidc/*` は APP_GUARD（IpAllowlistGuard）を通る**。チャネルで扱いを分ける:

- **バックチャネル（server-to-server）= 除外**: `/oidc/token`（token / introspection / revocation）・`/oidc/me`（userinfo）・`/oidc/jwks`・`/oidc/.well-known`。RP サーバーが発信する経路で、発信 IP は利用者ブラウザ IP と別系統のため許可リストに乗らない（同一ホスト構成では localhost 発信になり、許可リスト設定時に SSO が全停止する）。いずれも**エンドポイント自身の認証**を持つ（token=client_secret / me=bearer access token / jwks・.well-known=公開情報）ため、IP 制限を外しても認可境界は崩れない。
- **フロントチャネル（利用者ブラウザ）= 除外しない**: `/oidc/auth`・`/auth/interaction/*` は利用者のブラウザが叩く経路。SSO 利用者も「許可 IP 内からのアクセス」というネットワーク境界の既定方針に従わせる（認証方式に依らず IP 遮断を適用する原則の一貫適用）。

### 既知の運用上の注意（MEDIUM・残存）

- 遮断 IP は `ThrottlerGuard` 手前で弾かれるため rate limit を消費しない（フラッド時に DB へ届く前に 403 で返るが、TTL キャッシュ後は許可リスト取得自体が 15s に 1 回まで間引かれるため DB 負荷増幅は解消）。endpoint 単位の burst 制御が要るなら別途 throttle 設計（現状は許容）。

## §10 二層 rate 防御の協調（throttle × lockout・set-0025 P4）

認証経路には**役割の異なる2層の rate 防御**が同時に効く。両者は**独立に評価され、先に当たった方で拒否する**（片方を消すと他方の保護軸が無防備になるため、どちらも残す）。

| 層           | 守る軸                                | 実装                                                                                                              | 既定閾値                                                                                    | 状態の持ち方                                  | 超過時                                                                            |
| ------------ | ------------------------------------- | ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- | --------------------------------------------- | --------------------------------------------------------------------------------- |
| **throttle** | IP / endpoint 単位の短期 burst        | `@nestjs/throttler`（`ThrottlerGuard`・guard 段）                                                                 | グローバル 30 req/60s。`login`・`login/mfa` は 5 req/60s に強化。files fileId 列挙は 20/min | プロセスメモリ（既定 ThrottlerStorage）       | **429**（throttler 由来は `code` なし＝`AllExceptionsFilter` が status から導出） |
| **lockout**  | Account 単位の認証失敗（brute-force） | `AuthService.validateCredentials` / `AuthController.loginMfa` / `InteractionController.loginMfa`（H6 / ADR 0033） | 5 回連続失敗で 15 分ロック（`MAX_LOGIN_ATTEMPTS` / `LOGIN_LOCKOUT_MINUTES`）                | Account 行（DB）＝IP / インスタンス越えに一貫 | **429**（`code: TOO_MANY_REQUESTS` を明示）                                       |

### 評価順と「独立評価」の意味

ログイン1リクエストの通過順は `IpAllowlistGuard → ThrottlerGuard → controller(validateCredentials 内の lockout)`。よって**パイプライン上は throttle が先**に評価されるが、両層は**別の軸**を守るため独立に成立する:

- **throttle** は「この IP / endpoint からの単位時間あたりリクエスト数」を見る（資格情報の正否は問わない）。同一 IP からの高速連打を 5/60s で頭打ちにする。
- **lockout** は「この Account の連続失敗回数」を見る（IP を跨いでも DB カウントで一貫）。分散 IP から1アカウントを狙う総当たりを 5 回/15 分で止める。

片方だけでは穴が残る（throttleのみでは分散IPの低速総当たりを通し、lockoutのみでは単一IPの高速連打でDBへ失敗UPDATEが続く）ため**両方必須**。二系統の429を重複と誤認して一方を撤去しないこと。

### 補助カウンタ（MFA 段）

MFA チャレンジ（`POST /auth/login/mfa` と OIDC interaction の `login/mfa`）は、5回失敗で pending を破棄するsession内カウンタ（`MFA_LOGIN_MAX_ATTEMPTS`）に加えて、Account行のDB lockout counterにも失敗を加算する。passwordまたはMFAのいずれかで既定5回に達すると15分ロックとなり、IP・session・インスタンスを変えても回避できない。カウンタは全認証要素の成功後だけリセットし、password成功だけではMFA pending中の失敗を消さない。既存の環境変数 `MAX_LOGIN_ATTEMPTS` / `LOGIN_LOCKOUT_MINUTES` を共用する。

### 429 の区別（運用上の注意）

両層とも 429 を返すが、**lockout は `code: TOO_MANY_REQUESTS` を持ち、throttler 由来は `code` を持たない**（§1 error 体系）。ログ・監視で両者を区別したい場合は response body の `code` 有無で判別する。lockout の 429-vs-401 による email 実在 enumeration は UX 説明性を優先して許容（ADR 0033）。

## §11 マイグレーション運用ノート（task_activities・dsk-0289）

`task_activities` の CHECK 制約更新（DROP→ADD CONSTRAINT、field union へ値追加）は `20260624060000` / `20260627100000` / `20260703093500` と同型パターンが3回累積している。現状は**小テーブル・単一ユーザー運用のため即時検証（lock_timeout 未設定・NOT VALID 不使用）が正**——ロックで待たされる相手も存在せず、二段適用（NOT VALID+VALIDATE）へ切り替える利点がない一方、二段化は「既存データが旧許容値のみである事の即時検証」という現行マイグレーションの意図を捨てるだけになる。

**切替条件（このいずれかに該当したら見直す）**:

- 本番運用（マルチユーザー・同時接続）を開始した
- `task_activities` が大テーブル化した（マイグレーション実行時間・ロック待ちが無視できなくなった）

切替時の対処: 同型マイグレーションに `SET lock_timeout` / `SET statement_timeout` を設定する、または `ALTER TABLE ... ADD CONSTRAINT ... NOT VALID` → 別トランザクションで `VALIDATE CONSTRAINT` の二段適用へ切り替える。

## §12 migration 本文の適用後編集禁止（rete-system-0001）

DB へ適用した migration ファイルの本文は、**初コミット前であっても編集しない**。`_prisma_migrations` 台帳には適用時点の checksum が記録されるため、適用後に本文を書き換えると（単一コミットで履歴に編集が現れない場合も含め）台帳と現ファイルの checksum が恒久的に食い違い、次回 `prisma migrate dev` の素実行時に checksum 不一致→reset（開発 DB 全データ削除）要求という地雷になる（`migrate status` は checksum を検査しないため放置しても気づけない）。

**直したい変更が出たら**、適用済み migration の本文を触らず新規 migration を切って対処する。

### 復旧手順（既に食い違ってしまった時・cmn-0212）

禁止規範を破った後の出口が無いと、その場で一番手軽な「開発 DB 全消し（`migrate reset`）」に手が伸びる。**開発データを消さずに台帳と現ファイルを一致させる手順**は次のとおり（`prisma migrate dev` が「適用後に改変された」と報告して reset を要求してきた時に使う。cmn-0186 の作業中に実際に踏み、この手順で回避した）。

1. **状況を確定する** — 食い違っているのがどの migration かを `prisma migrate dev` の出力で特定する（`migrate status` が無警告でも食い違いが無い証拠にならないのは本節冒頭のとおり）。
2. **現ファイルの中身が、DB の現実と一致しているか**を先に確認する。台帳を書き換える操作は「ファイル＝適用済みの実体」と宣言する行為なので、ここが食い違ったまま進めると嘘の台帳が残る。一致していなければ、先に差分ぶんの新規 migration を切る（本文編集はしない）。
3. **台帳から当該行を削除する** — Prisma には checksum だけを更新するコマンドが無いため、削除して入れ直す形を取る。`prisma db execute` は SQL の入力元（`--file` / `--stdin`）と接続先（`--schema` / `--url`）の両方が必須なので、削除 SQL を1ファイル書いてから渡す。

   `DELETE FROM "_prisma_migrations" WHERE "migration_name" = '<migration_name>';` を `scratchpad/fix-checksum.sql`（gitignore 済み）に置き、リポジトリ直下から次を実行する（`--schema` は `DATABASE_URL` の解決に使う schema を指す）。

   ```bash
   pnpm --filter @rete/backend exec prisma db execute --file ../../scratchpad/fix-checksum.sql --schema prisma/schema.prisma
   ```

4. **現ファイルの checksum で登録し直す** — `pnpm --filter @rete/backend exec prisma migrate resolve --applied <migration_name>`。このコマンドは SQL を再実行せず台帳へ「適用済み」を記録するだけなので、行が残っていると失敗する（手順3→4 の順序は入れ替えられない）。
5. **確認** — `prisma migrate dev` が reset を要求せず通ることを確かめる。

**前提（適用範囲）**: 本手順は **食い違った migration が最新である場合**に検証済み（cmn-0186 の実例）。手順3-4 を通ると当該行の `started_at` / `finished_at` は再登録時刻になるため、**途中の migration** に当てると台帳上の適用順とディレクトリ順が入れ替わり、Prisma の履歴診断（histories diverge 系）に触れる可能性がある。途中の migration を直す必要が出たら、捨ててよい検証用 DB で「delete → resolve --applied → `migrate status` / `migrate dev`」を先に試してから本番の開発 DB へ適用すること。

**`migrate reset` は使わない**（開発 DB の全データが消え、seed のやり直しと手元で作った検証データの喪失を伴う）。本手順は**開発環境限定**であり、本番 DB の台帳を直接操作する必要が出た場合は §13 の本番運用方針の側で個別に判断する。

## §13 本番マイグレーション運用方針（rete-backend-0003）

MVP 規模（単一ユーザー・小テーブル）では実害の出ない書き方が、本番運用（マルチユーザー・大テーブル）では書込ブロック・長時間ロックの事故要因になる。適用済み migration の本文は §12 により編集禁止のため、直すのは「これからの書き方の規範」のみ。

### 13.1 大テーブルへの index 追加

数万行以内の小テーブルへの index 追加は非 `CONCURRENTLY` の即時 `CREATE INDEX` で問題ない。テーブルサイズがこれを超える場合は `CREATE INDEX CONCURRENTLY` を使い、書込みをブロックしない。

Prisma は各 migration をトランザクションで包んで実行するため、`CREATE INDEX CONCURRENTLY` を migration ファイルに直書きすると `cannot run inside a transaction block` で失敗する。該当時の手順:

1. migration ファイルには通常の `CREATE INDEX`（非 CONCURRENTLY）を書かず、SQL を別途手動生成する（`prisma migrate diff` 等）。
2. `CREATE INDEX CONCURRENTLY` を本番 DB へ **out-of-band（`psql` 等で直接）** 適用する。
3. 適用後 `prisma migrate resolve --applied <migration_name>` で `_prisma_migrations` 台帳を整合させる（実体を伴わない台帳登録）。

実例: trgm GIN index 4本（`20260619054617_add_trgm_search_indexes`）と、チャット検索用の trgm GIN index 3本（`20260727140000_add_chat_trgm_search_indexes` の `chat_messages_body_idx` / `chat_themes_title_idx` / `chat_themes_description_idx`）は非 CONCURRENTLY。`audit_logs` は全操作 INSERT のため、本番では書込ブロック要因になる。

### 13.2 型変更のオンライン化

`ALTER COLUMN ... SET DATA TYPE` は本番の大テーブルで full-table rewrite + `ACCESS EXCLUSIVE` ロックを起こし得る。該当する変更は以下のオンラインパターンを検討する:

1. 新しい型の列を追加する（`new_column`）。
2. アプリ側の二重書き込み or バックグラウンドジョブで既存データを `new_column` へ backfill する。
3. リネーム/スワップで `new_column` を本来の列名に差し替える。

実例: `tags`/`announcement_tags` の CITEXT 型変更（`20260619054721_tag_name_citext_unique`）は `ALTER COLUMN ... SET DATA TYPE CITEXT` で `ACCESS EXCLUSIVE`。本番での同種変更はこのパターンを検討する。

### 13.3 CHECK 制約の2段階適用

値追加時の CHECK 制約更新を `NOT VALID` → `VALIDATE CONSTRAINT` の2段階に切り替える判断基準・手順は **§11 を正本**とする（二重記述しない）。切替条件・対処法は §11 参照。

### 13.4 新規 FK 列の index 併設チェックリスト

PostgreSQL は FK 制約に自動で index を張らない。新規 FK 列を追加する migration では、**同一 migration 内で対応する index を併設する**。

- [ ] 新規 FK 列を追加する migration に `CREATE INDEX` が含まれているか
- [ ] 既存テーブルへの FK 列追加なら、上記 13.1（テーブルサイズに応じた CONCURRENTLY 要否）も併せて確認したか

実例: `task_comment` の FK 2本（`task_id`/`author_id`）のうち `task_id` のみ当初 index 併設、`author_id` は後続 migration（`20260623043108`）で追加という後追いが `task_activity`/`task_comment` で2回連続発生した。

### 13.5 新規 FK 制約の2段階適用（NOT VALID → VALIDATE CONSTRAINT）

既存テーブルへ `ADD CONSTRAINT ... FOREIGN KEY` を素で流すと、PostgreSQL は制約検証のために**参照元テーブル全体を走査する間 `SHARE ROW EXCLUSIVE` ロックを保持する**。行数が増えたテーブルではこの間 INSERT / UPDATE / DELETE が待たされ、実質的な書き込み停止になる。**大テーブルへの FK 追加は2段階に分ける**。

```sql
-- ① 既存行を検証せずに制約だけ張る（新規行にはこの時点から効く。ロックは短時間）
ALTER TABLE "child" ADD CONSTRAINT "child_parent_id_fkey"
  FOREIGN KEY ("parent_id") REFERENCES "parent"("id") NOT VALID;

-- ② 既存行の検証を後から流す（SHARE UPDATE EXCLUSIVE のみ＝書き込みを止めない）
ALTER TABLE "child" VALIDATE CONSTRAINT "child_parent_id_fkey";
```

判断基準は 13.1 と同じ**テーブルサイズ**。目安として数万行を超える参照元テーブルへ FK を足すなら2段階を選ぶ。空テーブル・新規テーブルへの FK は素の `ADD CONSTRAINT` でよい（検証対象が無いため）。

- Prisma の `migrate dev` が自動生成する FK は素の `ADD CONSTRAINT` になる。**生成された SQL を上記2段階へ手で書き換えてから適用する**（適用後の編集は §12 で禁止）。
- ②を①と別 migration に分ける必要はない。同一ファイル内で順に並べれば、ロックの重い区間だけが分離される。
- 13.4（FK 列への index 併設）と併せて確認する。

本方針は fil-0027 の `FolderPermission` 追加時点では実害ゼロ（新規テーブルで検証対象が無い）だが、**同じ書き方を大テーブルへ流用すると事故る**ため規範として先に置く（fil-0099 項目5）。既存 migration の書き換えは行わない（§12）。

### 13.6 不可逆 drop の事前確認手順

`DROP TABLE` / `DROP COLUMN` / `DROP TYPE` を含む migration は、適用後のデータ喪失が復元不能になる。**他環境（staging / 本番）へ適用する前に、対象データの分布を集計で「喪失ゼロ」を確認してから流す**。fixture = folder_permissions テーブル（fil-0136 で完全撤去）の撤去時の確認手順を具体例として残す。

```sql
-- 例: folder_permissions を drop する前の確認（grantee_type / level の分布）
SELECT grantee_type, level, COUNT(*) AS rows
FROM folder_permissions
GROUP BY grantee_type, level
ORDER BY grantee_type, level;

-- ALL/EDIT 以外（VIEW 等の段階権限）が 0 件であることを確認する。
-- 残存がある場合は、付与内容を退避してから drop する：
SELECT folder_id, grantee_type, grantee_id, level
INTO TEMP TABLE folder_permissions_preserve_20260803
FROM folder_permissions
WHERE level NOT IN ('ALL', 'EDIT');  -- 退避対象のみ抽出（全件でも可）
```

判定基準:

- **ALL/EDIT のみ**で件数 > 0 → 「既知の挙動変更（既定チャネル全メンバー可視化）」の範疇＝drop 可
- **ALL/EDIT 以外**で件数 > 0 → 復元不能な段階権限の喪失＝drop 不可。grant 経路を再確認し、補完 migration を先に出してから drop
- **空テーブル** → 0 件の明示確認後、drop 可

確認は drop を流す**前**に必ず実施する。drop 後の事後確認は不可（テーブルが存在しない）。確認者は記録（Board チケット・chat）に「集計結果 + 退避 SQL 実行有無」を残す。DBT-8 の本番ハードニングと合わせて、他環境デプロイ手順への反映を必須とする。

### 13.7 制約の張り替え（DROP CONSTRAINT + ADD CONSTRAINT）は単一 ALTER TABLE へ統合する

既存制約の変更（複合キーの組み換え等）で `DROP CONSTRAINT` と `ADD CONSTRAINT` を**別文**で書くと、2 文の間に制約が存在しない区間が開き、その窓で不正な行が入り込む（または検証なしの書き込みが通る）。**張り替えは単一の `ALTER TABLE` 文へ統合する**（実例 = fil-0149 の FK 張り替え・`folders` テーブル）:

```sql
-- 悪い例（2 文・制約不在の窓が開く）
ALTER TABLE "folders" DROP CONSTRAINT "folders_parent_folder_id_fkey";
ALTER TABLE "folders" ADD CONSTRAINT "folders_parent_folder_id_space_id_fkey"
  FOREIGN KEY ("parent_folder_id", "space_id") REFERENCES "folders"("id", "space_id")
  ON DELETE CASCADE ON UPDATE CASCADE;

-- 良い例（1 文・窓が開かない）
ALTER TABLE "folders"
  DROP CONSTRAINT "folders_parent_folder_id_fkey",
  ADD CONSTRAINT "folders_parent_folder_id_space_id_fkey"
    FOREIGN KEY ("parent_folder_id", "space_id") REFERENCES "folders"("id", "space_id")
    ON DELETE CASCADE ON UPDATE CASCADE;
```

- **適用対象は FK / CHECK 等の「真の制約」に限る**。Prisma の `@@unique` は unique index（`CREATE UNIQUE INDEX`）を生成するため `DROP CONSTRAINT` はエラーになり、index の張り替えは単一 ALTER TABLE に統合できない（該当ケースは別途 index の DROP / CREATE として扱う）。
- Prisma の `migrate dev` が自動生成する張り替えは別文になることがあるため、**生成された SQL を適用前に 1 文へ統合してから流す**（適用後の編集は §12 で禁止）。
- 既に適用済みの migration 本文は §12 により触らない（張り替え直しはしない）。本規範はこれから書く migration に適用する。
- 実例: `20260805140000_fil_0149_folder_composite_fk` が DROP と ADD を別文で含む（fil-0157 で確認・適用済みのため本文は不変・今後の規範として記録）。

## §14 Desk チャネル管理と PROJECT ADMIN membership（dsk-0355）

Desk 組織タブの「チャネルを追加／改名／アーカイブ」およびプロジェクト行の管理メニューは、**当該 PROJECT の scope-ADMIN membership**（`ProjectDto.canManageChannels`）があるときだけ表示される。

- **システム ADMIN（`Account.role=ADMIN`）でも、対象プロジェクトの PROJECT ADMIN membership が無ければメニューは出ない**（Desk 用 `GET /projects` に system ADMIN 特例を載せない方針・dsk-0355 案B／dsk-0309 と同根）。
- チャネル操作が必要なプロジェクトごとに、対象アカウントへ `scopeType=PROJECT` / `role=ADMIN` の membership を付与する（Settings メンバーシップ管理、または運用作業としての DB 付与）。
- テナント管理用の全件 ADMIN 一覧（`findAllAdmin`）は Settings 系に限り system ADMIN 特例あり。Desk サイドバーの一覧取得とは経路が別。

運用コスト（プロジェクト増ごとに個別付与）は既知。system ADMIN を Desk で常時 true にするコード変更は、権限モデル拡大として別判断が要るため本ポリシーでは採用しない。
