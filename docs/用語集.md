# 開発用語集（開発統括向け）

> 開発エージェントが rete 開発でよく使う用語を、非エンジニアの開発統括が読んで分かる平易な言葉でまとめたもの。過去の作業ログ・チケット・memory・規約から収集（2026-06-24 作成）。
>
> 困ったらカテゴリ見出しから引いてください。各用語は「概要（平易な説明）」だけ読めば足ります。

---

## 1. 開発フロー（Board v2 の1件処理）

開発エージェントの開発は Board v2 のチケット1件ごとに進む。現行の入口は `/dev-ticket`（1件を分類 → plan → 実装 → 検証 → 完了まで通す）で、変更のレビューは `/dev-review`、判断の記録は `/dev-adr` が担う。v1 の「設計 → 承認 → 製造 → 確認」と、それを担った `/dev-plan`・`/dev-design`・`/dev-code`・`/dev-decide`・`/dev-discover` は退役して使わない。

### /dev-plan（プラン）

退役済み。現行は着手前の承認ゲートを置かない。Board v2 の `/dev-ticket` が分類 → plan → 実装 → 完了までを AI 内部で進め、見た目や製品の挙動が変わるものだけ開発統括の受入へ渡す。

### /dev-design（デブデザイン｜設計フェーズ）— 退役済み

v1 は着手前の設計工程で、チケットを設計して開発統括の承認待ちに置いた（「要設計」→「設計済」）。現行は着手前の承認ゲートを置かず、`/dev-ticket` が着手時に受入条件（criteria）と作業記録（checkpoint）を plan で固定する。変更が4本以上または構造を動かす時は、plan を確定する前に `design-reviewer` が設計の前提を実体で裏取りする。

### /dev-code（デブコード｜製造フェーズ）— 退役済み

v1 は開発統括の承認後に回ってきたチケット（「要製造」）を受け取り、実装・検証・コミットまで完遂した。現行は `/dev-ticket` が実装・検証・証跡の登録・コミット・完了（見た目や製品の挙動が変わるものは受入待ち）までを1件で通す。

### /dev-decide（デブデサイド｜確認回答フェーズ・開発統括手番）— 退役済み

v1 は「要確認」のチケットを開発統括が一問一答でまとめて回答するための開発統括専用スキルだった。現行は AI が開発統括の判断を要する点だけを停止させ（待ち理由 `user_decision`）、1点ずつ問う。開発統括が Board で指示内容を編集して保存すると、新しい要求版の未着手（`open`）へ戻る。

### /dev-review（デブレビュー）

指定した変更・チケットを、実測した根拠を付けて点検するスキル。単独で呼ぶと読取専用で、計画と実体のズレ・チケット同士の重複や矛盾・未着手の棚卸しを検出して起票する。Board の独立レビュー（実装者とは別の主体が review artifact を投稿する）もこの技能で行う。

開発の実施状況ドキュメント（build-status.md）の鮮度は、git の実績と突き合わせる専用の技能（build-status-freshness-audit）が見る。

### /dev-discover（ディスカバー）— 退役済み

v1 は要件が曖昧なとき、短い質問のやり取りで「何をどこまで作るか」を固めた。現行は起票の時に目的と期待結果（`ui_metadata.intent`）を書き、開発統括の判断が要る点だけを `user_decision` の停止で問う。

### /chk-rete（チェックレテ）

rete の開発サーバー（画面側 :3010 / サーバー側 :3011）を再起動してヘルスチェックを行う1コマンド。実装後に必ず実行し、起動が壊れていないか確認する締めの操作。

## 2. Co-driver（共走）— 開発統括が判断する場面

AI は勝手に押し切らず、開発統括が決める場面（方向性・不可逆な操作・受入）では止まって相談する。「作ってから違う」を防ぐ。

### 正解像（せいかいぞう）

「どうなったら正解か」という完成の定義。AI が着手時に受入条件（criteria）として書き、Board の設計タブで読める。見た目や製品の挙動が変わる依頼では、この基準に沿って最後に開発統括の受入を受ける。

### 実行承認（じっこうしょうにん）— 退役済み

Board v1 の工程。開発統括が Board の「承認」ボタンを押すまで実装を始めない、という唯一の着手ゲートだった。現行の Board v2 はこのボタンを持たず、着手前の承認ゲートも置かない。AI は着手すると**分類 → plan → 実装 → 検証 → 完了**までを内部で進め、見た目または製品の挙動が変わるものだけを開発統括の最終確認（受入）へ渡す。

### co-driver（コードライバー）

開発統括を運転席の隣（co-driver）に置く開発スタイルの呼び名。承認ペース（実行承認ゲート）は退役したが、開発統括が決める場面で AI が止まることは変わらない。一方的な自律実装はしない。

### 設計ラリー（せっけいラリー）

開発エージェントと開発統括が一問一答を繰り返しながら要件・設計を固めていく作業。合意が固まるたびに仕様書やチケットの作業記録（`checkpoint`）・受入条件（`criteria`）へ逐次書き足し、会話だけに頼らない（後述の compact で消えないように）。

### choice-card（チョイスカード）

開発エージェントが Board のチケットに置ける「二択カード」。A案・B案を開発統括が1クリックで選べる。**押してもチケットの状態は変わらない**（相談の道具。状態を動かす操作ではない）。

## 3. チケットの状態（ステータス）

チケット＝作業の最小単位。今どの段階かを状態（state）で表す。Board v2 の state は4つ（open / active / waiting / closed）で、画面では3区分（対応中・最終確認待ち・完了）にまとまる。止まっている票は、理由を待ち理由（`waiting_reason`）で分ける。

| 画面の区分   | 表示名   | state（内部名）                    | 意味（誰のボールか）                                           |
| ------------ | -------- | ---------------------------------- | -------------------------------------------------------------- |
| 対応中       | 未着手   | `open`                             | 起票済みで、AI がまだ着手していない                            |
| 対応中       | 対応中   | `active`                           | AI が調査・実装・検証を進めている番                            |
| 対応中       | 停止中   | `waiting`                          | 実行が止まっている。理由は待ち理由で分かる                     |
| 最終確認待ち | 確認待ち | `waiting`（待ち理由 `acceptance`） | AI の作業が終わり、**開発統括の最終確認待ち**                      |
| 完了         | 完了     | `closed`                           | 受入済み、または開発統括の確認が要らない内部作業として AI が閉じた |

補足:

- **待ち理由（`waiting_reason`）** は「なぜ止まっているか」。環境の復旧待ち（`environment`）・前提待ち（`dependency`）・中断（`interrupted`）・やり直し（`retryable`）は、原因が解ければ AI が再開する。**開発統括の判断待ち（`user_decision`）** は開発統括の回答が要る。Board で指示内容を編集して保存すると、新しい要求版として未着手（`open`）へ戻る。
- **受入に回るかは AI の分類で決まる**。見た目または製品の挙動が変わる依頼は、出自（開発統括の直接起票・AI の検出）に関わらず開発統括の最終確認へ渡す。それ以外は AI が完了まで進める。
- **開発統括の答え方は Board のボタン**。成果が登録された最終確認待ちの票には「受け入れる」「修正を依頼する」が出て、受入済みの完了票は「受入を戻す」で最終確認待ちへ戻せる。
- **予定・後回しは state ではない**。対応区分（対応対象 / 予定 / 提案 / 後回し）として、state を変えずに付け外しする。
- **設計承認と製造承認を分ける2段の工程は無い**。v1 の工程語彙（要設計・設計済・要製造・製造済）は現行では使わない。

## 4. Board / Backlog（チケット管理ツール）

### Board（ボード）

チケット管理ツール**そのものの名前**（システム名 instruction-board v2、:3072 で動作・UI は `/v2.html`）。rete アプリの「バックログ」タブに埋め込み表示される。「Board を直して」＝このツールの改修。

### Backlog（バックログ）

Board に集まる**すべてのチケットの総称**（場所・概念）。「Backlog 処理」＝全システムのチケット作業に着手すること。Board（ツール）と区別して使い分ける。

### system（システム分類）

チケットがどのリポジトリ・サブシステムに属するかの分類。主な値は `rete`（本体）・`struct-pass-reference`（略 ref＝参照システム）・`instruction-board`（略 brd＝Board 自身）の3種。

### kind（種別）— v1 の欄

Board v1 はチケットの種類を `work`（作業依頼）と `plan`（開発計画チケット）の2つで持っていた。v2 に `kind` 列は無く、種類は `ui_metadata.ticket_type`（`feature`＝機能 / `bug`＝不具合 / `incident`＝障害。既定は `feature`）で持つ。

### criteria（受け入れ基準）

「これがこうなっていれば完了」という達成条件の箇条書き。着手時に 開発エージェントが書き、完了時に証跡（スクショ）と1項目ずつ照合する。解釈ズレを事前に潰す合意文書。

### design 欄 — v1 の欄

Board v1 はチケットの設計内容を書く欄を独立して持っていた。v2 に `design` 列は無く、設計は受入条件（`criteria`）と作業記録（`checkpoint`）として Board の設計タブに表示される。

### summary（概要）— v1 の欄

Board v1 は開発計画チケットの説明文を `summary` に置き、コミットから自動同期される body と別レイヤーで管理していた。v2 に `summary` 列も自動同期も無く、説明は起票時に書く本文（`request_body`）と題名（`title`）が持つ。

### plan_notes（プランノーツ）— v1 の欄

Board v1 は実装方針のメモを `plan_notes`（Board の画面には非表示）に置いていた。v2 に `plan_notes` は無く、実装方針は作業記録（`checkpoint`）に残す。

### 対応履歴（イベント記録とコメント）

作成・着手（`start`）・分類・plan・checkpoint・完了などの操作は、サーバーがイベントとして自動で記録する。記録は Board の対応履歴に並び、人が書くコメントも同じ場所に積まれる。v1 の「対応[旧]ブロックをチケット本文に書かないと 422 で進めない」という強制は無い。

### checkpoint（作業記録）

AI の作業の記録はチケットの `checkpoint` に残す（完了した作業・残る作業・試したこと・次の対応・作業中の変更・裏取り）。完了（complete）・block・編集権の返却（`yield-edit-rights`）のときに付けて送り、Board の設計タブで読める。

### 編集権（run）／ロック

着手するチケットを「掴む」仕組み。着手時に `start` して得た **run**（`run_id` と `lease_epoch`）が編集権を持ち、複数の 開発エージェントセッションが同じチケットを並行作業して二重実装になるのを防ぐ。有効期限は無く（時間切れで自動解放されない）、完了または block の後に返すまで保持される。取得から返却までの手順の正本は `docs/architecture/board-session-lock.md`。

### start / yield-edit-rights（編集権の取得と返却）

`start` は編集権（run）を取る操作。`yield-edit-rights` は完了または block の後に返す操作で、返すと run が ended になり `lease_epoch` が増え、掴んでいたパスが解放される。計画段階で「今回は手をつけない」と決めた場合も、block してから返して占有を残さない。`active` のチケットが残っていると `409 run_busy` で返せないため、先に完了または block する。

### 競合したときのエラー（409 / 403）

別の run が作業中のパスを掴もうとすると `409 path_conflict`、送った `lease_epoch` が古いと `409 stale_epoch`、所有していない run からの編集は `403 run_owner` で拒否される。その時はそのチケットに触らず、自分の run を取り直してから進める。

### 完了（complete）と受入（acceptance）

AI が作業を終えると、run から `complete` を送って結果（result）と証拠（evidence）を結び付ける。見た目または製品の挙動が変わる票は「最終確認待ち」（`waiting` の待ち理由 `acceptance`）になり、開発統括が Board の「受け入れる」「修正を依頼する」で判定する。それ以外は AI が完了（`closed`）にする。git のコミット文からチケットを探して自動で完了へ進める v1 の post-commit 同期は v2 には無い。

| 接頭辞 | 指すもの                              |

## 6. 開発トラックと進捗ドキュメント

### トラック

rete 開発を機能領域で束ねた管理単位。`desk / files / home / settings / hardening / common` がある。各トラックは計画書と進捗報告書のペアで管理される。

### build-plan.md（計画書）

そのトラックで「何を・どの順番で・どこまで作るか」を定義した骨格。進捗では書き換えない。

### build-status.md（進捗報告書）

そのトラックで実際に何が完了・進行中・未着手かの記録。git の実績と照合して更新する。将来は廃止予定（現在は延命中）。

### devplan-sources.json

どの計画書・報告書を Board に読み込ませるかを登録した設定ファイル。Board 本体（instruction-board）のルートに置く。

### hardening（ハードニング）

「堅牢化」の意味。本番公開に向けてセキュリティや堅牢性を強化する作業の総称（認証強化・権限制御の徹底・入力検証・不正ログイン対策など）。

## 7. 設計・意思決定の記録

### ADR（Architecture Decision Record）

重要な設計判断を残す記録。**採用した案だけでなく、検討して捨てた案と理由も**残す。後から同じ議論を繰り返さないため。`docs/decisions/0044-...` のような番号付きファイル。

### ADR 0044 — 退役した体制の記録

2026-06-22 確定の開発フロー大改訂の記録。旧フロー（/dev-loop・/dev-next・/dev-storming）を廃止し、`/dev-design`・`/dev-code`・`/dev-decide` の3スキル体制と6つの状態（要設計・設計済・要製造・製造済・要確認・Close）へ移行したことを定義した。**その体制は退役しており**、現行の入口は Board v2 の `/dev-ticket`（変更のレビューは `/dev-review`、判断の記録は `/dev-adr`）。この節は当時のフローがどう変わったかの記録として読み、v1 の手順を現行として使わない。

### /dev-adr（デブ・エーディーアール）

「規約からの意図的な逸脱」「複数案からの選択」「既知の不完全さの許容」「外部制約による選択」が起きたとき、その判断を ADR として記録するコマンド。

### 単一ソース（Single Source of Truth）

ある情報について「ここだけが正しい」とされる唯一の保存場所。複数箇所に同じ情報があると食い違うため、必ず1箇所を正本に定める。

### モデルタブ（正本）

rete 固有の共通仕様（UI ルール・用語・画面命名など）を一元管理する唯一の正本。アプリの `/model` 画面で閲覧でき、開発エージェントは実装前にここを読む。

### 捨て案 / negative knowledge

「試したが採用しなかった案とその理由」の記録。同じアイデアを後で別セッションが再び試して時間を無駄にしないための予防。

### 可逆性テスト（two-way door / one-way door）

ある判断が「1回の改修で別案に切り替えられるか（two-way＝可逆）」「切り替えると大コスト（one-way＝不可逆）」かを見る考え方。可逆なら 開発エージェントが自走決定、不可逆なら開発統括に確認。

## 8. 品質チェックとレビュー

### scale（スケール）— Tiny / Small / Medium / Large

変更の規模を4段階で分類するラベル。変更ファイル数が目安（Tiny＝1行修正、Small＝バグ修正、Medium＝新機能、Large＝16ファイル超の大規模）。スケールごとに手順の厳密さが変わる。

### quality cycle（品質サイクル）

実装後に複数のレビュー AI を同時に走らせ、問題を見つけて直す反復プロセス。Medium は最大2回、Large は最大3回。重大な問題が残れば次の回へ。

### code-reviewer / security-reviewer / database-reviewer

それぞれ「コード品質」「セキュリティ」「データベース」を専門に検査するレビュー AI（実働担当）。品質サイクルで並列起動する。

### CRITICAL / HIGH / MEDIUM / LOW（深刻度）

検出した問題の重大さの4段階ラベル。CRITICAL/HIGH は**必ず直してから**コミット・完了宣言する。MEDIUM/LOW は別チケットに退避して後回し可。

### /rev-arch・/rev-integrity・/rev-quality

コードを点検する3つのレビューコマンド。arch＝**構造**（設計ルール違反）、integrity＝**整合性**（命名の揺れ・ドキュメントとのズレ）、quality＝**品質**（セキュリティ・テスト・不要コード、修正まで実行）。

### drift（ドリフト）

ドキュメントとコードの実態が食い違っている状態（例：実装済みなのに「未着手」と記録されたまま）。「漂流」が語源。見つけたら**必ず是正**する。

### refactor-cleaner

使われていない関数・依存ライブラリ・ファイルを自動検出して安全に削除する道具。

## 9. 完了の検証（UI 変更時）

### UI Verification Gate（UI 検証ゲート）

画面の見た目や操作を変えた実装は、完了を宣言する前に**必ず1回は実際の画面を確認する**という決まり。スクショ比較か実ブラウザ操作で確認する。過去に「画面を見ずに完了」して差し戻しが32件出た反省から導入。

### 証跡駆動の完了検証

rete の UI チケットでは、完了時にスクショ等の証拠（証跡）を Board チケットに添付することを必須にするルール。「言った・言わない」の解釈ズレを証拠段階で防ぐ。

### before/after スクショ

変更前（before）と変更後（after）の画面写真。証跡添付に使う。

### verification-before-completion（完了前検証）

「動いた」と報告する前に、検証コマンドを実際に実行して出力を確認してから完了宣言するルール。「たぶん動いてる」で終わらせない。

## 10. アーキテクチャの約束事（不変条件）

コードの構造が崩れないための7つの約束。開発統括が直接触ることはないが、開発エージェントのコミットでよく出てくる。

### DTO 境界

API がデータを返すとき、データベースの内部形式をそのまま渡さず、専用の「送信用の形」（DTO）に変換してから返す約束。情報漏れと型ズレを防ぐ。

### Repository 分離

データベースへのアクセスを専用の窓口（Repository）に集約し、業務ロジックが直接 DB を叩かない約束。変更の影響範囲を限定できる。

### 2モジュール目の法則（コピペ禁止）

2つ目の機能が1つ目と80%以上同じなら、先に共通部品を抽出してから作る。「あとで共通化」は禁止（来ないため）。

### エラーハンドリングの一元化

各機能で個別にエラー処理を書かず、上位の共通受け口に集める。個別に書くと必ずどこか漏れる。

### shared 型の整合性

共通定義した「型（データの形）」は必ずどこかで使う。「定義したが未使用」は設計意図の嘘で、後で負債になる。

### hook 抽出

同じ画面パターンが3ページ以上で重複したら、共通部品（hook）に切り出す。

### 完了基準チェックリスト

機能の「完了」を宣言する前に確認する必須項目一覧。全項目に✅がついて初めて完了とみなす。

## 11. 用語ミニ辞典（その他よく出る語）

### CRUD（クラッド）

Create（作成）/ Read（読取）/ Update（更新）/ Delete（削除）の頭文字。データ操作の基本4種。「CRUD を作る」＝一覧・詳細・登録・編集・削除の一式を作る。

### ORM / Entity

ORM＝コードでデータベースを操作する変換ライブラリ（rete では Prisma）。Entity＝DBの1行に対応するデータの塊。Entity を外にそのまま返さないのが DTO 境界。

### migration（マイグレーション）

データベースの構造（テーブルや列）を変更する履歴スクリプト。段階的に適用してバージョン管理する。

### seed（シード）

開発環境を動かすための初期データ（管理者アカウント・サンプルデータ）を一括投入するスクリプト。

### env var（環境変数）

パスワード・接続先など「コードに直書きしてはいけない値」を外部から渡す仕組み。`.env` ファイル等で管理し、本番と開発で切り替えられる。

### healthcheck（ヘルスチェック）

サーバーが正常稼働しているか確認する専用 URL。監視ツールがここを叩いて死活を見る。

### dev watchdog（デブウォッチドッグ）

rete・reference・Board の dev サーバーを1分ごとに監視し、ダウンが続いたら自動再起動する Windows タスク。

### fire-and-forget

バックグラウンド処理の方式で「実行したら結果を待たない（失敗しても全体を止めない）」設計。失敗時はログにエラーを残すだけ。

### compact / context

context＝開発エージェントが今の会話で参照できる記憶の総量。長くなると限界に近づき、古い会話を要約圧縮するのが compact。要約で合意が消えるため、重要事項はファイルに書き出しておく。

### sub-agent（サブエージェント）

メインの 開発エージェントから独立した別の AI（実働担当）。code-reviewer などがこれ。別の記憶で動くのでメインの記憶を消費せず、安価なモデルに固定されている（本用語集もサブエージェントが収集）。

### permission / sandbox

Claude Code の実行制御の2層。permission＝「このコマンドを実行してよいか」の承認、sandbox＝OS レベルで実行できる操作の物理的な制限箱。許可ボタンを押しても sandbox の箱は開かない。

### 並列セッション

複数の 開発エージェントが同時に動いている状態。同じチケットの二重作業は、着手時に `start` で取得し `yield-edit-rights` で返す run の編集権が防ぐ。

### surgical changes（外科的変更）

依頼に直接関係しないコードは触らない約束。「ついでに直す」を禁止し、変更範囲を最小に絞る。

## セキュリティ用語

### RBAC（ロールベースアクセス制御）

「管理者（ADMIN）／一般メンバー（MEMBER）」などの役割に応じて、できる操作を制限する仕組み。

### RLS（行レベルセキュリティ）

データベースの行（レコード）単位でアクセス制御する仕組み。「自分のデータだけ見られる」を DB レベルで強制する。

### OIDC / SSO

OIDC＝「どのサービスでも同じアカウントでログイン」できる標準の仕組み。SSO（シングルサインオン）＝1回ログインすれば他システムにも自動ログインできる状態。rete にログインすると struct-pass-reference にも入れる。

### MFA / TOTP（二段階認証）

パスワードに加え、スマホの認証アプリのワンタイムコードでもログインを確認する方式。

### IDOR

本来見られないはずの他人のデータに、ID を直接指定してアクセスできてしまう脆弱性。

### XSS

攻撃者が悪意あるプログラムをページに埋め込み、他のユーザーのブラウザで実行させる攻撃。

### OWASP Top 10

ウェブアプリのセキュリティリスク上位10種の公式リスト。security-reviewer がこれを基準に検査する。
