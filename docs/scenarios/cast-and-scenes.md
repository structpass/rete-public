# rete 業務シナリオ — 登場ロール・キャスト・利用シーン定義

> このファイルは [`index.md`](./index.md)（シナリオ・カタログ）の**前段＝世界観バイブル**です。
> 「誰が（ロール／実在の人物像）」「どんな時間軸イベントで（利用シーン）」rete・struct-pass-reference・instruction-board を使うのかを定義し、
> index.md の各シナリオ（Given/When/Then）を**この実在キャストへ再キャスト**するための単一ソースにします。
>
> 目的は依然として **「そもそも通るか／想定できているか」** の確認と、**仕様未確定の炙り出し**。
> ここでは抽象的な「ADMIN／一般ユーザー」ではなく、**実名・実部門・実プロジェクト・実チャネル**で世界を固定し、現実の業務に近いやり取りを再現します。

## 0. 三システムの関係と世界観

rete はそれ単体ではなく、**基幹 WMS（struct-pass-reference）の協働サテライト**として導入される前提で世界を組みます。

| システム                       | 役割                                                                     | このキャスト世界での位置づけ                                                                                                                    |
| ------------------------------ | ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| **struct-pass-reference**      | 倉庫在庫管理（WMS）。発注→入荷→在庫→棚卸→出荷の物流フロー基幹            | 丸三産業の**現場が日々叩く基幹システム**。仕入先(Supplier)・運送(Carrier)・倉庫(Warehouse)・出荷先(顧客=destination) がここで動く               |
| **rete**                       | 協働サテライト。チャット／タスク／ファイル／お知らせ／バックログ         | 基幹の周辺で発生する**コミュニケーション・段取り・ファイル共有**を集約。reference とは SSO（rete=IdP／reference=RP）で連結                      |
| **instruction-board（board）** | 指示ボード。チケットで作業依頼・不具合報告・開発計画・障害通知を一元管理 | rete の「バックログ」タブに iframe 埋込。**不具合報告・システム障害通知**の起票先。アクターは開発統括(発注/承認)と開発エージェント(開発/報連相) |

### 三層のステークホルダ構造

```
        ┌─────────────────────────────────────────────┐
        │   導入企業：丸三産業株式会社（業務用食品・包装資材の卸＋物流）   │
        │   ├ 物流センター部門（倉庫オペレーション）                  │
        │   ├ 業務管理部（事務・発注・在庫管理）                     │
        │   └ 情報システム室（システム管理・テナント運用）             │
        └──────┬───────────────────────────┬──────────┘
               │ 発注/入荷（上流）              │ 出荷/納品（下流）
        ┌──────▼──────────┐         ┌────────▼─────────┐
        │ 下請け／ビジネスパートナー  │         │   顧客企業（注文元）    │
        │ ├ 仕入先：北関東フーズ    │         │ ├ セントラルキッチン高崎 │
        │ ├ 仕入先：ヤマト包材      │         │ └ ベーカリー三田      │
        │ └ 運送：東名運輸         │         └──────────────────┘
        └─────────────────┘
               外部関係者は rete の「連携チャネル」にゲスト参加（スコープ境界で可視範囲を制御）

        ┌─────────────────────────────────────────────┐
        │ システム提供／開発側（board 上の2者）                       │
        │ ├ 開発統括（起票・実行承認・クローズ）                           │
        │ └ 開発エージェント（設計・実装・報連相）                                │
        └─────────────────────────────────────────────┘
```

> **設計判断（要確認の論点）**: 仕入先・運送・顧客を rete に**ゲスト参加させるか**は運用方針。本定義では「連携チャネルにのみ membership を持つ外部ユーザー」として登場させ、**スコープ越境遮断（S-SPC-05）** の現実的な検証材料にする。なお現状 rete は実質シングルユーザー段階で、**チャネル参加者単位の可視性 enforcement は未配線（マルチユーザー移行で返済予定）** のため、これらゲスト境界シナリオの多くは ⚠ 将来挙動として扱う（後述 §5・§6）。

## 1. ロール定義

rete の権限は **3軸が直交**する（ADR 0025 二層 RBAC ＋ ADR 0037 Space モデル）。1人の人物は「システムRole × 業務ロール × 各Spaceのmembership role」を**独立に**持つ。

### 1-A. rete システムロール（テナント全体・`Account.role`）

| ロール                      | 何ができるか                                                                                                                                                                                                                                      | 重要な非対称                                                                                                                                                             |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **システム ADMIN**          | 管理系API全般（メンバー管理・招待・業務ロール定義・お知らせ変更・セキュリティ設定・監査ログ）。`FeaturePermissionGuard` を常時バイパス（業務ロール不問で chat/task/file 全CRUD）。`assertOwnerOrAdmin` 通過（他人の発話/タスク/添付を編集削除可） | ⚠ **Space 可視性だけはバイパスしない**＝テナント ADMIN でも**他人の個人メモ/DM は見えない**（ADR 0037 §3 プライバシー）。「ADMINなら全部見える」は個人スペースで破綻する |
| **システム MEMBER（既定）** | 読み取り系は素通し。管理系は 403。chat/task/file は**業務ロール次第**。自分の所有物のみ編集削除                                                                                                                                                   | 業務ロール未割当だと chat/task/file は**全 false＝実質何もできない**                                                                                                     |

> ADMIN 昇格 API は**現状なし**（seed/DB 直編集で付与）。`deserializeUser` が毎リクエストで DB から role を引き直すため、role 変更・ロックは**即時反映**。

### 1-B. rete 業務ロール（`RoleDefinition`・1アカウント1つだけ）

feature=`chat`/`task`/`file` の **CRUD 4粒度**（canRead/Create/Update/Delete）＋ feature=`system`（外部連携システムの**利用可否=canRead のみ**）。seed 同梱の4種：

| 業務ロール           | 権限の形                                                 | 想定する人物                       |
| -------------------- | -------------------------------------------------------- | ---------------------------------- |
| **倉庫オペレーター** | SYS-001(reference) read ＋ chat/task 限定（file なし等） | 倉庫現場の作業者                   |
| **事務管理者**       | 全 system ＋ chat/task/file 全 CRUD                      | 事務・発注のバックオフィス管理     |
| **閲覧専用**         | 全 read のみ                                             | 監査・閲覧だけの関係者             |
| **臨時応援**         | `isActive=false`（割当不可デモ）                         | 無効ロールの割当拒否を検証する材料 |

### 1-C. rete Space スコープロール（`Membership.role` per スコープ）

統一 Space モデル（ADR 0037）。階層＝**組織 ＞ プロジェクト ＞ チャネル**、横断の **グループ**、**個人**。

| スコープ種別                     | 作成権限                                            | ADMIN ができること                                         | MEMBER／可視性                                                                                                      |
| -------------------------------- | --------------------------------------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| **ORGANIZATION（組織＝事業部）** | 誰でも可（作成者が自動 ORG ADMIN）                  | 改名/archive・**配下プロジェクト作成**                     | membership を持つ組織のみ可視                                                                                       |
| **PROJECT（プロジェクト）**      | 親組織の ADMIN のみ                                 | 改名/archive・**配下チャネル作成/編集**・複数 ADMIN 任命可 | 可視組織配下で membership 可視                                                                                      |
| **CHANNEL（チャネル）**          | 親プロジェクト ADMIN のみ                           | （チャネル独立権限は無し）改名/archive は親PJ ADMIN        | ⚠ **チャネル単位の細粒度権限は設計上存在しない**＝親PJ membership で可視解決。非メンバーには**存在ごと隠す**（403） |
| **GROUP（組織非依存）**          | 誰でも可（作成者が GROUP ADMIN）                    | 改名/archive・メンバー招待/削除                            | membership を持つグループのみ                                                                                       |
| **PERSONAL_MEMO / DM（個人）**   | 本人（DM は相手指定・自分とのDM不可・ペア重複防止） | 更新不可                                                   | owner==self or peer==self のみ。**ADMIN でも他人のは不可視**                                                        |

> ⚠ **重要な未配線**: チャネル参加者の追加/削除に応じた可視性・権限の出し入れ（コンテンツ層 space enforcement）は**マルチユーザー移行まで未着手**（ADR 0038/0042・CM-D6/rete-common-0019）。「チャネル参加者を外したら見えなくなる」系シナリオは現状コードでは**効かない**＝⚠ 将来挙動。

### 1-D. reference（WMS）ユーザーロール（`UserRole`）

rederence 側は独自 3層 RBAC（ADR 0005＝authZ は reference 残置）。SSO で rete アカウント(sub) を `User.oidcSub` で引き当て。

| reference ロール         | 現場での役割                               |
| ------------------------ | ------------------------------------------ |
| **WH_USER（倉庫一般）**  | 入荷検品・出荷ピッキング・棚卸の現場作業   |
| **WH_ADMIN（倉庫管理）** | 倉庫長。倉庫マスタ・在庫調整の管理         |
| **OF_USER（事務一般）**  | 発注書起票・在庫/取引先マスタ更新          |
| **OF_ADMIN（事務管理）** | 業務管理の管理職。発注承認・マスタ統括     |
| **SYS_ADMIN**            | システム管理者。ユーザー/権限/全マスタ統括 |

### 1-E. board アクター

| アクター             | 行動                                                                                                                                                  |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| **開発統括**         | 起票（不具合報告・修正指示）／設計レビュー＆**実行承認**（designed→approved の「承認」ボタン＝唯一のゲート）／完了確認＆クローズ（waiting_user→done） |
| **開発エージェント** | 未承認チケットに正解像（design/criteria）を書き designed へ／承認済を実装→証跡添付→waiting_user で返す／判断観点はチケット化して問い合わせ            |

### 1-F. 組織ペルソナ・ロール（人物像の分類）

| ペルソナ                 | 所属                     | 典型的な rete／reference の使い方                                         |
| ------------------------ | ------------------------ | ------------------------------------------------------------------------- |
| **情シス管理者**         | 丸三産業 情報システム室  | テナント運用・招待・ロール定義・監査・セキュリティ設定・障害一次対応      |
| **倉庫担当**             | 物流センター部門         | reference で入荷/出荷/棚卸、rete で現場チャットと差異報告タスク           |
| **事務担当**             | 業務管理部               | reference で発注/マスタ、rete で仕入先・顧客との連携チャネル運用          |
| **仕入先（パートナー）** | 北関東フーズ／ヤマト包材 | rete 連携チャネルで納期調整・欠品連絡。reference の発注は相手方として登場 |
| **運送（パートナー）**   | 東名運輸                 | rete 配車チャネルで出荷スケジュール調整                                   |
| **顧客**                 | 高崎CK／ベーカリー三田   | rete 受発注チャネルで注文・問い合わせ。reference では出荷先 destination   |
| **開発／提供側**         | Struct Pass              | board でシステムの不具合報告・障害通知・改善要望に対応                    |

## 4. 利用シーン定義（時間軸イベント）

**新規** と付いたものは index.md に未収載＝今回のキャスト化で追加すべきシナリオ（特に運用イベント系）。

## 6. 次のステップ（このバイブルの使い方）

1. **index.md の既存シナリオを本キャストへ再キャスト** — 抽象「ADMIN／一般ユーザー」を高橋/加藤/高木…に置換し、前提を実部門・実チャネルで具体化する。
2. **運用イベント系シナリオ（P4/P5/P6 の「新規」）を index.md へ追加** — 退職・部署移動・脱退/復帰・事業部追加・チャネル参加者増減・管理者交代・障害通知・不具合報告。これらは現行 index.md の薄い領域。
3. **⚠ を仕様課題として収穫** — 未配線/未定義（チャネル可視性 enforcement・退職時データ処理・障害通知・IP遮断・管理者全消失ガード等）を index.md の「⚠ 仕様未確定一覧」へ転記し、必要なら board でチケット化。
4. **トラック横断の `.feature` 化** — 安定したシーンから `e2e/features/*.feature` へ昇格し E2E 自動化（運用正本 = `e2e/README.md`）。

> このファイルは**世界観の正本**。人物・部門・チャネルを増減する時はまずここを更新し、index.md／`.feature` がそれを参照する。
