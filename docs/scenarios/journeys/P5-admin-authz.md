# フェーズ P5 — 権限・管理者の交代（管理境界）

> このファイルは cast-and-scenes.md のフェーズ P5 を Given/When/Then に展開したジャーニーです。

> 範囲: システム管理者の交代（高橋→中村）／プロジェクト管理者の付け替え（伊藤→他PJメンバー・複数ADMIN）／チャネル管理の移譲（佐藤→鈴木・親PJ ADMIN経由）／非ADMINの認可境界試行（加藤・高木ほか）。
> 権限の事実: rete は **3軸直交**（システムRole × 業務ロール1つ × Space membership）。`deserializeUser` が毎リクエストで role を引き直すため **role 変更・ロックは即時反映**。システムADMINは FeaturePermissionGuard をバイパスし chat/task/file 全CRUD・他人編集可だが、**他人の個人メモ/DMは不可視**。業務ロール未割当は chat/task/file 全 false。チャネルは独立権限を持たず**親PROJECT membership で可視解決**。
> 権限の現況: 業務ロール層（RoleDefinition / RolePermission / UserSystemAccess / permissions-screen / FeaturePermissionGuard）は ADR 0077 で撤去済みで、現行は **2軸**（システムRole `Account.role` × 所属＝Membership / UserGroupScopeGrant）。本文の旅程は撤去前の設計時点の記録として残す（実装の正本ではない）。
> マルチユーザー化の enforcement（Space可視性・所有者チェック・cross-Space IDOR封鎖・assignee ドロップダウン・自分宛てメンション絞り込み）は実装済として **✅ 断定**で書く。それとは別理由で未定義の論点（ADMIN昇格専用API不在・最後のADMIN全消失ガード・退職時データ処理/OIDC失効/SLO）は **⚠** を維持する。

---

### P5-01 システム管理者の昇格（中村を ADMIN へ）

- **登場**: 高橋 健一（情シス室長・現ADMIN）、中村 彩（情シス担当・MEMBER）
- **システム**: rete members
- **前提(Given)**: 高橋が唯一のシステムADMIN。中村は情報システム室 ORG ADMIN だがテナント `Account.role` は MEMBER。情シスの管理業務を中村へ引き継ぐ方針。
- **操作(When)**: 高橋がメンバー画面（`/settings`）で中村の行を開き、システムアクセス（`Account.role`）を MEMBER → ADMIN に変更して保存。中村が再ログインせず次の操作（メンバー一覧の編集導線）を叩く。
- **期待結果(Then)**:
  - 中村の `Account.role` が ADMIN に更新され永続化される
  - 次リクエストの `deserializeUser` で role が引き直され、中村は再ログインなしで管理系API（メンバー管理・招待・ロール定義・監査・セキュリティ設定）に到達できる
  - ⚠ **システムADMIN昇格の専用APIは存在せず**、members 管理のシステムアクセス変更（=`Account.role` の直接更新）で代替している。「昇格」という業務操作に対応する明示的なエンドポイント/監査イベントが無く、誤って一般メンバーを ADMIN 化するリスクの歯止めが薄い
- **状態**: ⬜ ／ **仕様**: ⚠(ADMIN昇格専用APIが無くmembers管理のrole変更で実現＝仮定。昇格操作の独立性・監査の粒度が未定義)
- 対応: S-SET-01

### P5-02 旧管理者の降格と即時の管理API締め出し（高橋→MEMBER）

- **登場**: 中村 彩（昇格後ADMIN）、高橋 健一（退任側）
- **システム**: rete members
- **前提(Given)**: P5-01 で中村が ADMIN 化済み。高橋は管理職を離れるためテナント管理権を返上する。ADMIN は中村・高橋の2名いる状態。
- **操作(When)**: 中村がメンバー画面（`/settings`）で高橋の行のシステムアクセスを ADMIN → MEMBER に変更して保存。直後に高橋が操作ログ画面（`/settings/audit-log`）を開こうとする。
- **期待結果(Then)**:
  - 高橋の `Account.role` が MEMBER に更新される
  - 次リクエストの `deserializeUser` で role が反映され、高橋の管理系API（監査・メンバー管理・セキュリティ設定）はすべて 403 になり、UI から管理導線が消える
  - 高橋の業務ロール（事務管理者）は3軸直交で独立のため、chat/task/file の業務操作は引き続き可能（管理権のみ失う）
- **状態**: ⬜ ／ **仕様**: ✅

### P5-03 最後のADMINを降格させようとする（全消失ガード）

- **登場**: 中村 彩（唯一のADMINに戻った状態）
- **システム**: rete members
- **前提(Given)**: P5-02 の結果、テナントのシステムADMINは中村ただ1人。中村が誤って自分以外を探すが他にADMINはいない。
- **操作(When)**: 中村が自分の行のシステムアクセスを ADMIN → MEMBER に変更しようとする（あるいは別の運用ミスでADMINを誰も残さない操作を試みる）。
- **期待結果(Then)**:
  - ⚠ **「テナント内ADMINを0人にしない」全消失ガードは仕様未記載**。自己ロックアウト防止（自分自身の降格/ロック拒否＝P5-04）は実装済だが、それは「自分を守る」だけで、ADMIN が複数いる状況で順に降格して最終的に0人になる経路を塞ぐ保証は無い
  - 期待としては「最後の1人のADMIN降格は拒否されるべき」だが、現状この不変条件を担保するチェックが確認できず断定できない
- **状態**: ⬜ ／ **仕様**: ⚠(「最後のADMINを降格/ロックさせない」全消失ガード未記載。自己ロックアウト防止とは別の不変条件で、複数ADMINからの逐次降格経路が塞がれているか未確認)

### P5-04 自分自身の降格・ロックの拒否（自己ロックアウト防止）

- **登場**: 中村 彩（ADMIN）
- **システム**: rete members
- **前提(Given)**: 中村は現役のシステムADMIN。誤操作で自分の権限を落とす/自分をロックする操作を試みる。
- **操作(When)**: 中村がメンバー画面（`/settings`）で**自分自身の行**に対し、システムアクセスを MEMBER へ変更、あるいはアカウントロック（`isActive=false`）を実行しようとする。
- **期待結果(Then)**:
  - 自己ロックアウト防止により、**自分自身の ADMIN 降格・自分自身のロックは拒否**される（操作中のADMINが自らを締め出して管理不能になる事故を防ぐ）
  - エラー応答が返り、role/`isActive` は変更されない
- **状態**: ⬜ ／ **仕様**: ✅

### P5-05 プロジェクト管理者の追加任命（伊藤→小林・複数ADMIN）

- **登場**: 伊藤 千夏（新商品導入PJ ADMIN）、小林 拓也（同PJメンバー・発注担当）
- **システム**: rete projects / memberships
- **前提(Given)**: 「2026春 新商品導入PJ」の ADMIN は伊藤のみ。伊藤の業務集中を緩和するため、発注主担当の小林を共同管理者にする。PROJECT は複数 ADMIN を任命可。
- **操作(When)**: 伊藤が新商品導入PJの membership 管理画面で小林の `Membership.role` を MEMBER → ADMIN に変更。小林が配下チャネル（#高崎CK受発注）の改名や新チャネル作成を試みる。
- **期待結果(Then)**:
  - 小林の当該PROJECTでの `Membership.role` が ADMIN になり、伊藤と小林の **ADMIN 2名が並立**する
  - 小林は親PJ ADMIN として配下チャネルの作成/改名/archive・参加者管理が可能になる
  - 伊藤の ADMIN 権限は維持される（付け替えではなく増員）
- **状態**: ⬜ ／ **仕様**: ✅
- 対応: S-SPC-02, S-SPC-03

### P5-06 プロジェクト管理権の付け替え（旧ADMINの降格）

- **登場**: 伊藤 千夏（新商品導入PJ 旧ADMIN）、小林 拓也（新ADMIN）
- **システム**: rete projects / memberships
- **前提(Given)**: P5-05 で小林が新商品導入PJの共同 ADMIN 化済み。伊藤は業務管理部 ORG 管理に専念するため、当PJの ADMIN を返上し MEMBER に戻る。
- **操作(When)**: 小林（または伊藤自身）が伊藤の `Membership.role` を ADMIN → MEMBER に変更。直後に伊藤が同PJ配下に新チャネルを作成しようとする。
- **期待結果(Then)**:
  - 伊藤の当該PROJECTでの role が MEMBER になり、**配下チャネル作成/改名/archive・参加者管理は拒否**される（親PJ ADMIN 専権のため）
  - 伊藤はメンバーとしての可視・発話・タスク操作（業務ロール準拠）は維持
  - PROJECT の ADMIN は小林として存続（管理者ゼロにならない）
- **状態**: ⬜ ／ **仕様**: ✅
- 対応: S-SPC-02

### P5-07 チャネル管理の移譲（佐藤→鈴木・親PJ ADMIN経由）

- **登場**: 佐藤 大輔（物流センター長・在庫精度改善PJ 起案者）、鈴木 一郎（入荷担当）
- **システム**: rete space / memberships
- **前提(Given)**: 「在庫精度改善PJ」配下 #入荷検品 の運用を、これまで仕切ってきた佐藤から現場の鈴木へ移したい。チャネルは独立した管理権限を持たず、運用責任の移譲は**親PROJECT の ADMIN 付与**で表現するしかない。
- **操作(When)**: 佐藤が在庫精度改善PJ の membership で鈴木の `Membership.role` を MEMBER → ADMIN に変更し、#入荷検品 の参加者管理・改名権を鈴木へ渡す。
- **期待結果(Then)**:
  - 鈴木が在庫精度改善PJ の ADMIN になり、その権限で **#入荷検品 を含む配下チャネルすべて**の改名/archive・参加者追加削除が可能になる
  - ⚠ **チャネル単体への限定的な管理移譲はできない**（チャネル独立権限が設計上存在しない）。「#入荷検品 だけ鈴木に任せ、#棚卸差異 には触らせない」という粒度は表現不能で、PJ全体の管理権が付く副作用がある
- **状態**: ⬜ ／ **仕様**: ⚠(チャネル独立権限が無く親PJ ADMIN付与でしか移譲できない＝チャネル単位の限定移譲という業務要求に粒度が合わない。仕様としての割り切りの是非が未確定)
- 対応: S-SPC-03

### P5-08 チャネル参加者の出し入れと可視性の即時反映（移譲後の運用）

- **登場**: 鈴木 一郎（#入荷検品 を任された新PJ ADMIN）、加藤 直樹（臨時パート・membership なし）
- **システム**: rete memberships / desk
- **前提(Given)**: P5-07 で鈴木が在庫精度改善PJ ADMIN に。加藤は同PJに membership を持たず #入荷検品 は不可視。応援要員として一時的に #入荷検品 を見せたい。
- **操作(When)**: 鈴木が在庫精度改善PJに加藤を MEMBER として追加（冪等 upsert）。加藤がサイドバーを再描画し #入荷検品 を開く。検品繁忙が終わり、鈴木が加藤を当PJから削除する。加藤が再度 #入荷検品 を開こうとする。
- **期待結果(Then)**:
  - 追加後、加藤は親PJ membership により #入荷検品 が一覧に出現し、テーマ/スレッドを閲覧できる（チャネル可視性は親PROJECT membership で解決）
  - 削除後、#入荷検品 は加藤の一覧から消え、直接URL/詳細アクセスは 403 で**存在ごと隠される**
  - ただし加藤は業務ロール未割当のため、可視期間中も発話/タスク作成は全 false（閲覧のみ＝P5-10と連動）
- **状態**: ⬜ ／ **仕様**: ✅
- 対応: S-SPC-04, S-SPC-05

### P5-09 業務ロール未割当ユーザーの無力境界（加藤）

- **登場**: 加藤 直樹（臨時パート・業務ロール未割当）
- **システム**: rete desk / files
- **前提(Given)**: 加藤はシステムRole=MEMBER、業務ロール=未割当。P5-08 で #入荷検品 の親PJに一時 membership を持つ（=Spaceは可視）。
- **操作(When)**: 加藤が #入荷検品 でチャットテーマを作成、発話を投稿、タスクを起票、ファイルを添付しようとする。それぞれの操作APIを叩く。
- **期待結果(Then)**:
  - chat/task/file の **Create/Update/Delete はすべて FeaturePermissionGuard で入口拒否**（業務ロール未割当＝feature 権限が全 false）
  - read 系（テーマ/スレッド/タスクツリーの閲覧）は Space 可視範囲内で通る＝「見えるが何も書けない」状態
  - Space membership があっても業務ロールが無ければ書き込みは一切できないことを、3軸直交として確認できる
- **状態**: ⬜ ／ **仕様**: ✅
- 対応: S-FILE-11, S-DESK-07

### P5-10 無効な業務ロール（臨時応援）の割当拒否

- **撤去注記**: 業務ロール層は ADR 0077 で撤去済み。本ステップが操作する「業務ロールの割当」は現行 UI に存在しない（撤去前の設計時点の記録）。
- **登場**: 高橋 健一（または中村・ADMIN）、加藤 直樹（割当対象）
- **システム**: rete members / roles
- **前提(Given)**: seed 同梱の業務ロール「臨時応援」は `isActive=false`（無効ロールの割当拒否を検証する材料）。ADMIN が加藤に業務ロールを与えようとする。
- **操作(When)**: ADMIN がメンバー画面（`/settings`）で加藤の業務ロールに「臨時応援」を割り当てて保存しようとする。
- **期待結果(Then)**:
  - `isActive=false` のロール定義は割当不可で、保存は拒否（BadRequest 相当）される
  - 加藤の業務ロールは未割当のまま変わらない
  - 有効な業務ロール（例: 閲覧専用）であれば割当成功することと対比できる
- **状態**: ⬜ ／ **仕様**: ✅

### P5-11 越境遮断（閲覧専用ゲストが他チャネル・設定APIを試行）

- **登場**: 高木 茂（北関東フーズ営業・閲覧専用・#北関東フーズ連携のみ）
- **システム**: rete desk / settings / space
- **前提(Given)**: 高木は社外ゲストで membership は #北関東フーズ連携 の親PJ（新商品導入PJ）のみ、業務ロールは閲覧専用（全 read のみ）。
- **操作(When)**: 高木が (1) 別チャネル #高崎CK受発注 / #東名運輸・配車 を一覧・詳細で参照、(2) 物流センター ORG や在庫精度改善PJ のデータを参照、(3) `PATCH /files/settings` などの管理系API、(4) お知らせ作成APIを順に叩く。
- **期待結果(Then)**:
  - (1)(2) membership を持たない Space は**一覧に出ず、直接アクセスは 403**（存在ごと隠蔽）。可視は #北関東フーズ連携 とその親PJ可視範囲に限定
  - (3) 管理系設定は非ADMINのため一律 403
  - (4) お知らせ作成は 403、UIに作成導線が出ない
  - 閲覧専用ロールなので、可視チャネル内でも read のみ（発話作成/編集は不可）
- **状態**: ⬜ ／ **仕様**: ✅
- 対応: S-SPC-05, S-SET-07, S-HOME-07, S-FILE-10

### P5-12 他人の発話・タスク・添付の編集境界（所有者チェック）

- **登場**: 山本 翔（棚卸担当）、加藤 直樹（一般・他人）、中村 彩（システムADMIN）
- **システム**: rete desk / files
- **前提(Given)**: #棚卸差異 で山本が「ロット差異▲12ケース、原因調査中」という発話と関連タスク・添付（棚卸差異一覧.xlsx）を作成済み。加藤と中村が当該Spaceを可視。
- **操作(When)**: (1) 加藤が山本の発話を編集/削除、山本のタスクの担当/期限を変更、山本の添付を解除しようとする。(2) 中村（ADMIN）が同じ操作を行う。
- **期待結果(Then)**:
  - (1) 加藤は `assertOwnerOrAdmin` で**所有者でもADMINでもない**ため拒否（403）。発話3経路・タスク・添付の所有者チェックが効く
  - (2) 中村は ADMIN として `assertOwnerOrAdmin` を通過し、他人の発話/タスク/添付を上書き・削除できる
  - 編集後の内容が永続化され、ツリー/スレッドに反映
- **状態**: ⬜ ／ **仕様**: ✅
- 対応: S-DESK-07

### P5-13 cross-Space IDOR の封鎖（添付GET・分類CRUDの所有権チェック）

- **登場**: 高木 茂（#北関東フーズ連携のみ・閲覧専用）、松本 由美（在庫精度改善PJのファイルヘビーユーザー）
- **システム**: rete files / categories / attachments
- **前提(Given)**: 松本が在庫精度改善PJ配下で分類（categories）と添付を多数管理。高木はそのSpaceに membership を持たないが、添付ID・分類IDを推測または流用できる立場と仮定。
- **操作(When)**: 高木が (1) 自分の可視範囲外の添付を `GET /attachments/:id` で直接取得、(2) 在庫精度改善PJ配下の分類を別Spaceから更新/削除しようとする。
- **期待結果(Then)**:
  - (1) 添付GET は対象の所属Space所有権をチェックし、可視範囲外IDは 403（ID直打ちの cross-Space IDOR を封鎖）
  - (2) 分類 CRUD も Space 所有権チェックで、自分の所属外Spaceの分類は更新/削除不可（403）
  - IDが正しく推測できても、membership に基づくスコープ所有権で弾かれる
- **状態**: ⬜ ／ **仕様**: ✅
- 対応: S-FILE-10, S-DESK-12

### P5-14 ADMINでも他人の個人メモ・DMは不可視（ADMIN権の上限）

- **登場**: 中村 彩（システムADMIN）、渡辺 美咲・大野 守（DM当事者2名）、松本 由美（個人メモ所有者）
- **システム**: rete space（PERSONAL_MEMO / DM）
- **前提(Given)**: 渡辺と大野が #東名運輸・配車 の配車調整に関連して個人DMで1対1連絡。松本が個人メモに取引先マスタの作業メモを保存。中村はテナント全権のシステムADMIN。
- **操作(When)**: 中村が監査/トラブル調査の名目で、渡辺⇔大野のDMスレッド、および松本の個人メモを一覧・詳細で参照しようとする。
- **期待結果(Then)**:
  - DM は `peer==self` でない中村には**不可視**（一覧に出ず詳細アクセスは拒否）。第三者DMはADMINでも見られない
  - 個人メモも `owner==self` でない中村には不可視
  - 「システムADMINなら全部見える」は個人スペース（PERSONAL_MEMO/DM）で破綻する＝ADR 0037 のプライバシー不変条件として Space 可視性だけは ADMIN バイパスしないことを確認
- **状態**: ⬜ ／ **仕様**: ✅
- 対応: S-SPC-05

### P5-15 退職に伴う管理権返上とアカウント停止（管理境界×ライフサイクル）
