# フェーズ P6 — 障害・トラブル対応（不具合報告・障害通知・ログイン不可）ジャーニー

> このファイルは cast-and-scenes.md のフェーズ P6 を Given/When/Then に展開したジャーニーです。

トラブル対応は「現場が困る → 誰に・どう伝わる → 直る／解除される」の連鎖で世界が動く。ここでは丸三産業の実部門・実チャネルと、board 上の開発統括／開発エージェントを使い、ログイン不可の一次対応・不具合報告の起票フロー・障害通知の連絡経路・board 落下時の表示を具体化する。
中核の⚠は2系統ある。**(I) 障害／運用通知は operational-policy §7.1 で明確に「持たない」**＝自動配信は無実装で、障害連絡は現状すべて手動（チャット／お知らせ／電話・メール等の外部連絡）に頼る。**(II) ログインロック解除・問い合わせ対応・MFA 復旧（管理者リセット）のフローが未定義**。マルチユーザー化で配線された認可境界（可視性・所有者チェック・IDOR 封鎖）は別軸として now enforced で断定する。

---

### P6-01 ログインできない（連続失敗でスロットル）→自然解除待ち

- **登場**: 三田 誠（ベーカリー三田 店主・小口顧客・閲覧専用）／高橋 健一（情シス室長・ADMIN）
- **システム**: rete auth
- **前提(Given)**: 三田は #高崎CK受発注 ではなく小口・随時参加で、久々のログインでパスワードを失念。`/login` で誤ったパスワードを立て続けに送信する。ログイン throttle は「60秒で6回試行・5回超で429」。
- **操作(When)**:
  1. 三田が `/login` でメール＋誤パスワードを 6 回連続送信する。
  2. 6 回目で弾かれ、三田は高橋へ電話で「ログインできない」と問い合わせる。
  3. 高橋は throttle が時間経過で自然解除される旨を伝え、約1分待ってから正しいパスワード（または再設定）で再試行するよう案内する。
- **期待結果(Then)**:
  - 5 回超過の時点で `429`（ブルートフォース抑制）が返り、それ以上の試行は一定時間ブロックされる。
  - throttle はアカウント無効化ではなく一時的レート制限であり、待機後に正しい資格情報でログインできる。
  - ⚠ 高橋（ADMIN）側に「このアカウントのロック状態を確認・即時解除する」管理導線は未定義＝対応は「待ってもらう」口頭案内に留まる。
- **状態**: ⬜ ／ **仕様**: 429 スロットル自体は✅（対応: S-AUTH-09）／ロック状態確認・即時解除フローは⚠（管理者向けロック解除UIが未定義）

### P6-02 ログインできない（招待トークン期限切れ）→再招待待ち

- **登場**: 三田 誠（小口顧客）／中村 彩（情シス担当・招待運用）
- **システム**: rete invite / auth
- **前提(Given)**: 三田は受発注連携のため中村から招待メールを受け取ったが、多忙で放置し token の有効期限が切れた。「リンクを開いても先に進めない」と問い合わせる。
- **操作(When)**:
  1. 三田が期限切れの `/invite/accept?token=...` を開く。
  2. 受諾に失敗するため、三田は中村へ「招待リンクから登録できない」と連絡する。
  3. 中村は `/settings/invites` で当該 PENDING 招待を再送（token 再生成・expiresAt 延長）する。
- **期待結果(Then)**:
  - 再送により token が再生成され expiresAt が延長され、三田は新しいリンクで受諾→アカウント作成できる（対応: S-INV-05）。
  - ⚠ 失効 token を開いた時の三田側のエラー表示・「管理者に再招待を依頼する」導線が未定義＝三田は何が起きたか分からず電話に頼る（対応: S-INV-06）。
- **状態**: ⬜ ／ **仕様**: 再送導線は✅（S-INV-05）／失効時のユーザー向けエラー表示・再招待導線は⚠（S-INV-06）

### P6-03 ログインできない（TOTP端末紛失→バックアップコードで自力復旧）

- **登場**: 渡辺 美咲（出荷担当・MFA有効）／高橋 健一（ADMIN）
- **システム**: rete auth / mfa
- **前提(Given)**: 渡辺は MFA（TOTP）有効。スマホを機種変更し認証アプリの TOTP が再取得できず、パスワードは通るが 2 段階目で詰まる。MFA セットアップ時に発行されたバックアップコードを保管している。
- **操作(When)**:
  1. 渡辺が `/login` でパスワード認証を通過し、MFA チャレンジ画面に到達する。
  2. TOTP が打てないため、保管していたバックアップコードを入力する。
- **期待結果(Then)**:
  - バックアップコードで full session が確立しログインできる（対応: S-AUTH-03）。
  - 使用済みバックアップコードは single-use で無効化され、再利用できない。
  - ログイン後は新端末で TOTP を再セットアップする運用が望ましい（誘導は本人判断）。
- **状態**: ⬜ ／ **仕様**: ✅（S-AUTH-03・single-use 無効化）

### P6-04 ログインできない（TOTPもバックアップコードも喪失）→管理者リセット要求

- **登場**: 鈴木 一郎（入荷担当・MFA未設定→強制設定で設定済の想定）／高橋 健一（ADMIN）
- **システム**: rete auth / members
- **前提(Given)**: MFA 強制下で設定を済ませた鈴木が、端末紛失かつバックアップコードも紛失。自力復旧の手段が尽き、高橋へ「2段階認証が突破できずログインできない」と問い合わせる。
- **操作(When)**:
  1. 鈴木が MFA チャレンジで TOTP もバックアップコードも入力できない。
  2. 高橋がメンバー画面（`/settings`）で鈴木の MFA をリセット（再セットアップ要求）しようとする。
- **期待結果(Then)**:
  - 鈴木はバックアップコード喪失時、自力ではログインを完了できない（single-use コードは再発行されない）。
  - ⚠ 管理者が他ユーザーの MFA を強制リセットして再セットアップへ戻す専用フローは未定義＝メンバー編集 UI にその導線があるか不明。DB 直編集に頼る可能性。
  - ⚠ リセット後に MFA 強制が効いていれば、鈴木は再ログイン直後に再セットアップへ誘導される（S-AUTH-08 と同型）想定だが、リセット起点の経路は未検証。
- **状態**: ⬜ ／ **仕様**: ⚠（管理者による MFA 強制リセット／復旧フローが未定義・DB 直編集依存の懸念）

### P6-05 ログインできない（退職ロック済アカウント）→これは仕様どおりの遮断

- **登場**: 渡辺 美咲（退職対象・`isActive=false`）／高橋 健一（ADMIN）
- **システム**: rete auth / members
- **前提(Given)**: 渡辺は退職に伴い高橋が `Account.isActive=false` でロック済。本人（または事情を知らない第三者）が古い資格情報でログインを試みる。
- **操作(When)**:
  1. ロック済アカウントで `/login` にメール＋正しいパスワードを送信する。
  2. （あるいは退職前から開いていた別タブで保護ページを操作し続ける）
- **期待結果(Then)**:
  - 認証は即時に `401` で遮断される（`deserializeUser` が毎リクエストで DB から状態を引くため、ロックは次リクエストで即反映）。
  - これは不具合ではなく仕様どおりの遮断であり、ログイン不可の問い合わせが来ても「アカウント停止済」と回答すべき正常系。
  - ⚠ 退職者が reference（WMS）側に張っていた OIDC grant／SSO セッションは TTL 自然失効まで生存し得る（SLO＝単一ログアウト未定義）。rete ロック＝reference 即時遮断ではない。
- **状態**: ⬜ ／ **仕様**: rete 側 401 即遮断は✅（isActive=false）／reference 側セッション失効・OIDC grant 失効・SLO は⚠（未定義）

### P6-06 業務ロール未割当者が「タスクが作れない」を不具合と誤認して報告

- **登場**: 加藤 直樹（臨時パート・業務ロール未割当）／佐藤 大輔（物流センター長・ORG ADMIN）／高橋 健一（ADMIN）
- **システム**: rete desk / members
- **前提(Given)**: 加藤は業務ロール未割当で、システムRole は MEMBER。chat/task/file は全 false。現場で「タスクを作ろうとするとボタンが効かない／弾かれる」と感じ、佐藤へ「システムが壊れている」と報告する。
- **操作(When)**:
  1. 加藤が desk でチャット発話・タスク作成・ファイル添付を試みる。
  2. 佐藤がこれを不具合と疑い、高橋に確認を依頼する。
  3. 高橋がメンバー管理で加藤の業務ロール割当状態を確認する。
- **期待結果(Then)**:
  - 加藤の chat/task/file 操作は `FeaturePermissionGuard` で入口拒否され、create 系 API は 403 を返す（対応: S-FILE-11）。これは仕様どおりで不具合ではない。
  - 一覧・読み取り系は素通しのため「見えるのに作れない」状態になり、誤認を生みやすい。
  - 解決は不具合修正ではなくロール割当（高橋が「倉庫オペレーター」等を割当）で、割当後は権限が即時反映される。
- **状態**: ⬜ ／ **仕様**: 入口 403 拒否は✅（業務ロール未割当＝全 false）／⚠「権限不足で操作不可」を不具合と取り違えさせない UX（理由提示・無効ボタンの説明）は弱い

### P6-07 システム不具合の報告（棚卸差異画面の挙動不良→board work チケット起票→開発エージェント対応）

- **登場**: 山本 翔（棚卸担当）／伊藤 千夏（業務管理部主任・橋渡し）／開発統括（board 起票・承認）／開発エージェント（開発）
- **システム**: reference / board
- **前提(Given)**: 山本が reference の棚卸（Stocktaking）で差異登録を行った際、保存後に件数表示が更新されない不具合に遭遇。rete 上で開発統括に届く経路を持たないため、伊藤経由で開発統括へ連絡が回る。
- **操作(When)**:
  1. 山本が「棚卸差異の確定後に一覧の差異件数が古いまま」を伊藤に報告。
  2. 開発統括が board v2（:3072）に不具合内容を作業依頼チケット（`kind=work`）として起票する。
  3. 開発エージェントが原因調査→正解像を design/criteria に書き designed へ→開発統括が「承認」ボタンで実行承認→開発エージェントが修正・証跡添付→waiting_user。
  4. 開発統括が完了確認しクローズ（done）。
- **期待結果(Then)**:
  - 不具合は board のチケットとして一元管理され、起票→設計→実行承認→実装→確認→クローズの流れで処理される（対応: S-MISC-01/02）。
  - ⚠ board に bug/incident 専用 kind は無く `kind=work` を流用する＝不具合・通常依頼・障害が同じ kind に混在し、種別での絞り込み・集計ができない。
  - ⚠ 現場（山本）から開発統括／開発エージェントへ届く正規の報告導線は未整備で、人手（伊藤）を介する。rete 内に「不具合を起票する」現場向け入口は無い。
- **状態**: ⬜ ／ **仕様**: board での起票〜クローズ運用は✅（S-MISC-01/02）／bug/incident 専用 kind 不在・現場からの報告導線未整備は⚠

### P6-08 システム障害発生時の通知・連絡（reference 障害→board 起票＋手動連絡）

- **登場**: 高橋 健一（情シス・障害一次対応）／開発統括（board）／開発エージェント（一次調査）／小林 拓也・松本 由美ら社内利用者
- **システム**: reference / board / rete（手動連絡）
- **前提(Given)**: reference（WMS）が応答しなくなり、発注・入荷・出荷の現場操作が止まる。rete の「システム」タブからの reference 起動確認 probe がグレー化し、高橋が障害を検知する。operational-policy §7.1 によりインシデント／運用通知は「持たない」＝自動配信は無実装。
- **操作(When)**:
  1. 高橋が reference 無応答を検知し、開発統括が board に障害チケット（`kind=work` 流用）を起票、開発エージェントが一次調査に入る。
  2. 高橋が社内利用者へ「WMS 障害中・復旧見込み」を周知しようとする。
- **期待結果(Then)**:
  - 障害の起票・調査・復旧対応は board 上で進む。
  - ⚠ 障害発生を利用者へ自動配信する仕組みは無い（§7.1「持たない」）。周知は高橋が手動で rete お知らせ作成・チャット投稿・口頭などに頼る。
  - ⚠ rete お知らせ（全社配信）は届く範囲が広いが、障害連絡専用テンプレや配信対象の絞り込み（影響部門のみ）は無く、運用次第。
  - reference 起動確認 probe のグレー化はクライアント no-cors fetch による reachability 表示で、障害「検知」にはなるが「通知」はしない。
- **状態**: ⬜ ／ **仕様**: probe による reachability 表示は✅／障害通知の自動配信は⚠（§7.1 で持たない・手動連絡前提）

### P6-09 障害時の社外パートナー連絡（東名運輸への配車影響連絡）

- **登場**: 大野 守（東名運輸・配車担当・#東名運輸・配車のみ可視・閲覧専用）／渡辺 美咲（出荷担当）／高橋 健一（ADMIN）
- **システム**: rete desk / home / 外部連絡（電話・メール）
- **前提(Given)**: WMS 障害で当日の出荷登録が止まり、東名運輸の配車に影響が出る。大野は社外ゲストで #東名運輸・配車 のみに membership を持つ（他チャネル・全社情報は不可視）。
- **操作(When)**:
  1. 渡辺が #東名運輸・配車 に「本日 WMS 障害で出荷確定が遅延、配車時刻の後ろ倒しを相談したい」と投稿する。
  2. 高橋が全社お知らせで障害を周知したと仮定し、大野にも伝わるかを確認する。
- **期待結果(Then)**:
  - 大野は #東名運輸・配車 内の投稿は閲覧でき、渡辺の連絡は届く（可視性 enforcement により大野は所属チャネル内のみ参照可）。
  - 大野は他チャネル・他部門の情報には一切アクセスできず（一覧に出ず 403）、社内全体の障害状況は見えない。
  - ⚠ 全社お知らせの配信対象に社外ゲストが含まれるか（届くべきか）は運用未定義。実務上は障害連絡が確実に届く保証が無く、電話・メール等の外部連絡に二重化するのが現実的（§7.1 手動連絡前提）。
- **状態**: ⬜ ／ **仕様**: チャネル可視性 enforcement（所属内のみ参照・越境 403）は✅／社外ゲストへの障害周知到達保証は⚠（手動外部連絡前提）

### P6-11 board 停止中のコミット同期取りこぼし（復帰後の整合）

- **登場**: 開発エージェント（開発）／開発統括（board）
- **システム**: board（post-commit autosync）／rete misc
- **前提(Given)**: board 停止中に 開発エージェントがチケット ID 付きコミットを行う。通常は post-commit フックがコミットメッセージの ID を抽出して waiting_c2/sent_back→waiting_user へ自動遷移＋ロック解放するが、board API が落ちていると同期 POST が届かない。
- **操作(When)**:
  1. board 停止中に 開発エージェントが `fix(...): ... (dsk-0xxx)` をコミットする。
  2. post-commit フックが board へ状態同期を試みるが、:3072 無応答で失敗する。
  3. 後刻 board が復帰し、開発統括が当該チケットを開く。
- **期待結果(Then)**:
  - post-commit 同期は非ブロッキング設計のため、board 無応答でもコミット自体は成功し開発は止まらない。
  - ⚠ board 復帰後、停止中コミット分のチケットが自動で waiting_user へ追従するか（後追い再同期があるか）は未確認＝waiting_c2 のまま取り残され、開発統括の確認待ち表示と実体（実装済）がドリフトする可能性。
  - 取りこぼし時は次回の手動操作（PUT）かコミット時の再フックで是正される想定だが、保証は未検証。
- **状態**: ⬜ ／ **仕様**: ⚠（board 停止中コミットの状態同期取りこぼし・復帰後の再同期保証が未検証＝チケット状態ドリフト懸念）
