# フェーズ P0 — 立ち上げ・準備（システム管理者が設定を入れる）ジャーニー

> このファイルは cast-and-scenes.md のフェーズ P0 を Given/When/Then に展開したジャーニーです。

丸三産業株式会社が rete（協働サテライト）と struct-pass-reference（WMS）を導入する初日。情報システム室の高橋室長がテナントのセキュリティ設定・業務ロール定義・SSO 開通を行い、物流センター長の佐藤と業務管理部主任の伊藤が自部門の器（組織→プロジェクト→チャネル）を立ち上げる。本フェーズは「現場が使い始める前の土台」を固める工程で、正常系のほか **認可境界（非 ADMIN による設定改変の遮断）・誤操作（不正 CIDR）・未配線/未定義の炙り出し（IP 遮断・ポリシー違反 UX・事業部初期払い出し）** を併せて検証する。

---

### P0-01 パスワードポリシーの初期設定

- **登場**: 高橋健一（情シス室長・システム ADMIN）
- **システム**: rete settings（`/settings/login-settings`・PATCH `/settings`）
- **前提(Given)**: 高橋がシステム ADMIN としてログイン済。テナントは導入初日でパスワードポリシー未設定（既定値）。社内規程は「最小12文字・英大小+数字+記号・90日有効期限」。
- **操作(When)**: セキュリティ設定画面でパスワードポリシー（最小長 12・複雑性要件 ON・有効期限 90日）を入力して保存する。
- **期待結果(Then)**:
  - ポリシーが全置換方式で保存され、再読込後も保持される。
  - 以降に発行する招待受諾時のパスワード登録（井上ら）はこのポリシーで検証される前提が成立する。
- **状態**: ⬜ ／ **仕様**: ✅(アサート可能) 対応: S-SET-05

### P0-02 不正 CIDR の入力拒否（誤操作）

- **登場**: 高橋健一（システム ADMIN）
- **システム**: rete settings（PATCH `/settings`・IP 許可リスト）
- **前提(Given)**: 高橋が IP 許可リストに本社グローバル IP レンジを登録しようとしている。
- **操作(When)**: IP 許可リスト欄に不正な値 `192.168.0.300/24`（オクテット範囲外）と `10.0.0.0/40`（プレフィクス長不正）を含めて保存する。
- **期待結果(Then)**:
  - サーバ側 CIDR 検証で不正値が弾かれ、400/バリデーションエラーで保存が拒否される。
  - 正しい CIDR のみ（例 `203.0.113.0/24`）なら全置換で保存される。
- **状態**: ⬜ ／ **仕様**: ✅(アサート可能) 対応: S-SET-05

### P0-03 IP 許可リストは保存されるが遮断は効かない

- **登場**: 高橋健一（システム ADMIN）／渡辺美咲（出荷担当・テスト用に社外 IP からアクセス）
- **システム**: rete settings / auth
- **前提(Given)**: 高橋が IP 許可リストに社内レンジ `203.0.113.0/24` を保存済（P0-02 の正常分）。渡辺がリスト外の自宅回線 IP からログインを試す。
- **操作(When)**: 渡辺がリスト外 IP から `/login` にアクセスし、正しいメール+パスワードで認証する。
- **期待結果(Then)**:
  - リスト外であるにもかかわらずログインが成立してしまう（遮断されない）。
  - ⚠ IP 許可リストは設定として保存されるだけで、リクエストを遮断する middleware が未配線（hardening 別件で保存のみ・遮断は効かない）。「IP 制限が掛かっている」と運用者が誤認するリスクがある。
- **状態**: ⬜ ／ **仕様**: ⚠(未確定: IP 遮断 middleware が未実装＝保存のみ。リスト外アクセス時の拒否挙動／ブロック画面／エラーコードも未定義) 対応: S-AUTH-10

### P0-04 パスワードポリシー違反時の UX が未確定

- **登場**: 高橋健一（システム ADMIN）／井上涼（新入社員・受諾時にパスワード登録）
- **システム**: rete settings / invite/auth
- **前提(Given)**: P0-01 のポリシー（最小12文字・複雑性要件）が保存済。井上が招待受諾画面でパスワードを設定しようとしている。
- **操作(When)**: 井上が `pass123`（ポリシー違反＝短く記号なし）を入力して登録を試みる。
- **期待結果(Then)**:
  - ⚠ どこで弾くか（クライアント即時／サーバ受諾時）・違反メッセージの文言・有効期限切れ時の強制変更フローが未定義。受諾が通ってしまうのか、無言で失敗するのか確定できない。
- **状態**: ⬜ ／ **仕様**: ⚠(未確定: ポリシー違反時の弾く場所・メッセージ・期限切れ強制変更が未定義) 対応: S-AUTH-11

### P0-05 MFA 強制（enforced）を有効化する

- **登場**: 高橋健一（システム ADMIN）／中村彩（情シス担当・MFA 強制の旗振り）
- **システム**: rete settings（`/settings/login-settings`・MFA enforced フラグ）
- **前提(Given)**: テナントの MFA は任意設定の状態。高橋・中村・佐藤・渡辺・伊藤・小林は MFA 設定済だが、鈴木・山本・松本・井上・社外パートナー各位は未設定。
- **操作(When)**: 高橋がセキュリティ設定で「MFA を全社員に強制（enforced）」を ON にして保存する。
- **期待結果(Then)**:
  - テナント設定に MFA 強制フラグが保存され、即時反映される（`deserializeUser` が毎リクエストで引き直すため次回ログインから有効）。
  - 既に MFA 設定済の高橋らは挙動変化なし。未設定者には次回ログイン時の誘導が掛かる（P0-06 へ波及）。
- **状態**: ⬜ ／ **仕様**: ✅(アサート可能) 対応: S-SET-05

### P0-06 MFA 強制の波及＝未設定者が次回ログインで設定へ誘導される

- **登場**: 鈴木一郎（入荷担当・MFA 未設定）
- **システム**: rete auth/mfa
- **前提(Given)**: P0-05 で MFA 強制が ON。鈴木は MFA 未設定のまま、入荷検品の朝に rete へログインしようとする。
- **操作(When)**: 鈴木が `/login` でメール+パスワード認証に成功する（パスワードは正しい）。
- **期待結果(Then)**:
  - 認証は成立するが、MFA 未設定のため通常の `/hub` ではなく `/settings/login-settings`（MFA セットアップ）へ誘導される（toast 案内付き）。
  - 鈴木は setup→otpauth 取得→TOTP 確認→有効化を済ませるまで強制設定フローに留まる。
- **状態**: ⬜ ／ **仕様**: ✅(アサート可能) 対応: S-AUTH-08 ／ S-SET-04

### P0-07 業務ロール 3 種を定義する

- **登場**: 高橋健一（システム ADMIN）
- **システム**: rete settings（業務ロール定義・`RoleDefinition`）
- **前提(Given)**: テナントは seed 同梱ロールのみ。高橋が現場区分に合わせて業務ロールを整備する。業務ロールは 1 アカウント 1 つ、feature=chat/task/file の CRUD 4 粒度＋feature=system（外部連携の利用可否=canRead のみ）。
- **操作(When)**: 高橋が次の 3 ロールを作成・権限設定する。
  - 倉庫オペレーター: SYS-001(reference) read ＋ chat/task 限定（file 権限なし）
  - 事務管理者: 全 system ＋ chat/task/file 全 CRUD
  - 閲覧専用: 全 feature read のみ
- **期待結果(Then)**:
  - 3 ロールが作成され、以降のメンバー割当で選択肢に出る。
  - 倉庫オペレーターを割り当てた鈴木は後に file 操作を試すと FeaturePermissionGuard で拒否される土台が成立する。
- **状態**: ⬜ ／ **仕様**: ✅(アサート可能) 対応: S-SET-02

### P0-08 無効な業務ロール「臨時応援」を定義しておく（割当拒否の材料）

- **システム**: rete settings（業務ロール定義）
- **前提(Given)**: 臨時パートには将来「臨時応援」ロールを使いたいが、運用上まだ有効化しない方針。

- **期待結果(Then)**:

  - 後続（P1-5）でこの無効ロールを加藤へ割り当てようとすると拒否される前提が成立する。
- **状態**: ⬜ ／ **仕様**: ✅(アサート可能) 対応: S-SET-02

### P0-09 非 ADMIN によるセキュリティ設定変更の遮断（認可境界）

- **登場**: 松本由美（マスタ管理・システム MEMBER／事務管理者ロール）
- **システム**: rete settings
- **前提(Given)**: 松本はシステム MEMBER。業務ロールは事務管理者（chat/task/file 全 CRUD）だが、これは feature 権限であってテナント管理権ではない。
- **操作(When)**: 松本が `PATCH /settings`（パスワードポリシー／IP 許可リスト更新）API を直接叩く。
- **期待結果(Then)**:
  - 403 で一律拒否される（管理系 API はシステム ADMIN のみ）。事務管理者ロールを持っていてもセキュリティ設定は変更できない（業務ロールとシステム Role は直交）。
  - UI 上もセキュリティ設定の編集導線が出ない。
- **状態**: ⬜ ／ **仕様**: ✅(アサート可能) 対応: S-SET-07

### P0-10 組織（事業部）の器を作成・作成者が自動 ADMIN

- **登場**: 佐藤大輔（物流センター長）／伊藤千夏（業務管理部主任）／高橋健一（情シス室長）
- **システム**: rete space（ORGANIZATION 作成・`Membership.role`）
- **前提(Given)**: 統一 Space モデル（ADR 0037）で組織は誰でも作成でき、作成者が自動で ORG ADMIN になる。
- **操作(When)**:
  - 佐藤が組織「物流センター」を作成
  - 伊藤が組織「業務管理部」を作成
  - 高橋が組織「情報システム室」を作成
- **期待結果(Then)**:
  - 3 組織が作成され、それぞれ作成者（佐藤・伊藤・高橋）が当該 ORG ADMIN として membership を持つ。
  - 各人は membership を持つ組織のみ可視（他組織は一覧に出ない＝後述 P0-12/越境の前提）。
- **状態**: ⬜ ／ **仕様**: ✅(アサート可能) 対応: S-SPC-01

### P0-12 チャネルの器を作成（親 PJ ADMIN のみ・チャネル独立権限は無い）

- **登場**: 伊藤千夏（新商品導入PJ ADMIN）／佐藤大輔（在庫精度改善PJ ADMIN）

- **前提(Given)**: P0-11 でプロジェクトが作成済。チャネルは親プロジェクト ADMIN のみ作成でき、チャネル単位の独立権限は設計上存在せず、可視性は親 PJ membership で解決される。
- **操作(When)**:

### P0-14 reference 連携（SSO）の開通確認

- **登場**: 高橋健一（システム ADMIN・reference は SYS_ADMIN）
- **システム**: rete ↔ reference（OIDC・rete=IdP / reference=RP）
- **前提(Given)**: rete→reference の SSO は実装完成済で有効化済（`REFERENCE_OIDC_READY=true`）。高橋は rete にログイン済セッションを持つ。両スタック（rete・reference）が起動している。
- **操作(When)**: 高橋が rete の Hub「システム」導線から reference（WMS）へ遷移し、OIDC interaction（login prompt→consent）を経て reference に入場する。
- **期待結果(Then)**:
  - rete アカウント（sub）が reference 側で `User.oidcSub` により SYS_ADMIN ユーザーに引き当てられ、reference のダッシュボードに入場できる。
  - SSO 経路が開通していることが確認でき、以降の現場ユーザー（鈴木の入荷検品・小林の発注）が同経路で WMS を叩ける土台が成立する。
- **状態**: ⬜ ／ **仕様**: ✅(アサート可能) 対応: S-AUTH-04 ／ S-AUTH-05

### P0-15 再認証なし（silent）SSO の挙動は実装済み

- **登場**: 高橋健一（システム ADMIN）
- **システム**: rete ↔ reference（OIDC）
- **前提(Given)**: 高橋は rete に有効セッションを保持。reference 側から `/login?uid=...` 経由で SSO 入場した直後、続けて reference を再度開く。
- **操作(When)**: 既存 rete セッションがある状態で reference へ再入場し、consent やパスワード再入力を求められず通過する。
- **期待結果(Then)**:
  - silent SSO（再認証・consent 省略）は実装済み。reference 401 検知時に FE 401 interceptor がトップレベル遷移で `GET /auth/oidc/silent-login?return=<path>` を発火し（reference 側 `oidc.controller.ts:130` `silentLogin` ハンドラ）、`prompt=none` 付きで rete に問い合わせる。rete 側は既存セッションがあれば `interaction.controller.ts:78` で login prompt をパスワードなしで完了させ、returnUrl へリダイレクトする。`/login` を戻り先に許すと 401 → silent-login → `/login` の無限ループになるため、サニタイズで除外している。
- **状態**: ⬜ ／ **仕様**: ✅(アサート可能: silent SSO は実装済み) 対応: S-AUTH-04（の裏）／ cmn-0149 chk-ref スモークで導通確認可能

### P0-16 システム ADMIN でも他人の個人スペースは不可視（管理権の非対称）

- **登場**: 高橋健一（システム ADMIN）／佐藤大輔・鈴木一郎（個人 DM の当事者）
- **システム**: rete space（PERSONAL_DM）
- **前提(Given)**: 立ち上げ後、佐藤と鈴木が個人 DM で 1 対 1 のやり取りを始めている。高橋はシステム ADMIN で管理系全権・他人の発話/タスク/添付は編集削除可。
- **操作(When)**: 高橋が監査目的で佐藤↔鈴木の個人 DM を参照しようとする。
- **期待結果(Then)**:
  - システム ADMIN であっても他人の個人 DM／個人メモは不可視（owner==self or peer==self のみ・ADR 0037 §3 プライバシー enforce 済）。
  - 「ADMIN なら全部見える」は個人スペースで破綻する＝管理権の境界が立ち上げ時点で明確化される。
- **状態**: ⬜ ／ **仕様**: ✅(アサート可能) 対応: S-SPC-05（の裏・プライバシー境界）
